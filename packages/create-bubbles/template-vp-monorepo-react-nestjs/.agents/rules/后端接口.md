# 后端接口

## 适用范围与依据

- 新增、修改或重构后端 HTTP 接口，以及调整请求校验、访问策略、响应、异常或接口文档前，必须读取本规则。
- 同时按根目录 [AGENTS.md](../../AGENTS.md) 读取命中的代码设计、共享代码和需求与设计文档规则。本规则适用于本次涉及的接口，不要求顺带迁移无关历史接口。
- API 协议以 [API 与统一错误技术契约](../../.spaces/07.API与错误/技术契约.md) 为准；原生校验与响应处理依据 [NestJS 原生 Schema 迁移需求](../../.spaces/07.API与错误/NestJS原生Schema迁移/需求文档.md)。新需求先更新所属 `.spaces/` 文档，再开始实现。

## 契约、类型与职责

- 实现前明确请求方式、路径、Body／Query／Param、返回字段、HTTP 状态、登录要求、操作权限、数据范围和失败场景；变更已有接口时检查调用方及兼容性。
- 前后端请求和返回类型统一放在 `packages/shared/src/types`，复用方法放在 `packages/shared/src/utils`。运行时 Schema 放在后端所属功能目录，并通过 `satisfies z.ZodType<共享类型>` 等类型约束保持一致，不在前后端重复定义公开协议。
- Controller 负责接收、校验和转交请求，Service 负责业务规则与数据操作；遵循功能目录、JSDoc 和超过 3 个参数改用对象传参的既有约定。

## 请求运行时校验

- 新增或改造请求参数时，优先通过 NestJS 原生参数装饰器的 `schema` 选项接入 Zod Schema，复用全局 `StandardSchemaValidationPipe`；不得只靠 TypeScript 类型、类型断言或 Swagger 注解校验请求。
- 按契约覆盖 Body、Query 和 Param 的必填项、长度、数值范围、枚举、ID 格式、数组上限及跨字段约束。明确可选字段、`null`、空字符串、默认值和未知字段的处理策略，未知字段应拒绝或剥离。
- Query 和 Param 中需要数值或布尔值的字段必须显式转换；分页须有默认值和每页上限，筛选和排序字段须使用白名单，不能直接信任客户端提供的数据库字段或 SQL 片段。
- 业务必须使用 Schema 校验并转换后的值；账号可按契约规范化，密码、令牌等字段不得擅自 trim 或改变内容。
- 守卫先于参数 Pipe 执行。权限解析依赖的路由 ID 仍须在守卫使用前校验，复用现有提前校验方法；已有手动 parse 仅在明确需要的场景保留，并转换为 `COMMON.VALIDATION_FAILED` 与安全字段详情。

## 登录、权限与数据范围

- 每个接口必须声明适用的访问策略：公开接口用 `@Public()`，仅要求登录的接口用 `@Authenticated()`，受业务权限保护的接口用 `@AccessPolicy()`。未声明策略的受保护接口默认拒绝，不能靠改成公开接口解决访问失败。
- 当前认证使用 Redis Session 的 Bearer Token；操作者身份来自已验证的认证上下文，不接受请求正文中的 `userId`、角色或管理员标记作为身份和权限依据。
- 登录、操作权限和资源归属分别校验。企业／项目 ID、资源 ID 及请求头只是待验证输入，必须确认资源属于当前作用域，相关成员、角色和资源状态允许操作。
- 查询和更新条件应包含已验证的数据范围，禁止只凭资源 ID 跨企业或项目读写；批量接口中的每个关联资源都须校验归属和权限。
- 涉及权限或资源状态变化的写操作，应在事务中复核相应权限、归属和状态，避免只依赖进入 Controller 前的守卫结果。

## 成功响应与业务异常

- 成功响应直接返回业务正文，不增加通用 `{ code, data, message }` 外壳；Controller 和 Service 的公开返回类型应使用共享契约，HTTP 状态与接口行为保持一致。
- 新增 JSON 成功响应或调整公开字段时，定义响应 Schema 并接入 `@SerializeOptions({ schema })`，复用全局 `StandardSchemaSerializerInterceptor`。Service 同样只选择允许公开的字段，不能依靠序列化器兜底泄露内部数据。
- 密码哈希、内部凭据和无权读取的字段不得出现在公开响应。令牌仅在认证契约明确允许的响应字段中返回。文件流、下载流和无正文响应按各自协议处理，不套用普通 JSON Schema；失败响应不套用成功响应 Schema。
- 业务失败通过模块的稳定错误定义抛出 `AppException`，交给 `GlobalExceptionFilter` 统一处理；不得返回 HTTP 200 表示业务失败，也不得在 Controller 自行拼装另一种错误外壳或吞掉未知异常。
- 失败正文遵循 `{ code, message, details? }`，无有效详情时省略 `details`。请求校验失败为 HTTP 400／`COMMON.VALIDATION_FAILED`；响应 Schema 失败属于安全的 HTTP 500。401 的 Bearer 质询通过错误定义声明，其他状态按契约选择。
- 公开文案和详情不得泄露原始异常、堆栈、SQL 或连接信息；内部原因可通过 `cause` 保留，由统一日志机制脱敏。成功和失败响应继续保留 `x-request-id`，日志不得记录原始密码、Authorization、Cookie、令牌或密钥。

## 数据一致性与查询成本

- 必须一起成功的数据库修改放在同一事务中；唯一性以数据库约束兜底，不能仅靠“先查再新增”。数据库与 Redis、对象存储或队列的操作不具备天然跨系统原子性，应按业务确定失败恢复或补偿方式。
- 已使用 `expectedVersion` 的资源更新、删除继续在数据库写入条件中校验版本，冲突按既有契约处理；新业务根据并发风险选择版本校验、锁或条件更新，避免覆盖他人修改。
- 会被重试且产生重复副作用的写操作应明确幂等策略；删除、重复提交及资源不存在时的语义写入契约，不能仅由前端按钮禁用保障。
- 列表查询限制数量、使用稳定排序并避免逐条额外查询；耗时任务按当前队列能力处理，外部调用设置合理超时，重试须与幂等语义一致。

## Swagger 与验证

- **本项目当前保留 Swagger。** `/api-docs` 和 `/api-docs-json` 提供接口文档，新建或修改接口时同步接口用途、请求参数、成功响应、主要失败响应、HTTP 状态和认证声明。
- 使用 NestJS 原生 Schema 与 Swagger 的 `standardSchema` 支持复用运行时 Schema，不为文档维护另一套字段定义，也不重新引入 `nestjs-zod` 的 `createZodDto`、`cleanupOpenApiDoc` 等旧适配。
- `@ApiBearerAuth('session')` 描述当前 Session Token 的 Bearer 认证，是否使用 JWT 不决定是否保留此配置。Swagger 文档注解不等于鉴权，运行时校验、`@SerializeOptions` 和访问策略须分别正确接入。
- 如有明确需求停用 Swagger，先更新正式需求与契约，再清理文档启动配置、注解和无其他用途的依赖；保留请求校验、响应校验、鉴权和业务类型。
- 按本次接口风险验证正常请求、非法参数、未登录、权限不足、跨企业或项目访问、公开字段及错误结构；有相应写入风险时增加重复提交、版本冲突和事务回滚验证。Schema 转换、字段剥离或权限策略有变动时，应验证真实 HTTP 调用链。
- 运行项目要求的格式、类型、测试和必要构建检查，将实际结果归档到所属 `.spaces/` 功能目录。替身测试、跳过项和未连接的数据库／Redis／对象存储必须明确记录，不能写成真实服务集成通过。
