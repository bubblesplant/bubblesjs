# 上传文件内容去重与业务引用

> 状态：服务端原生 crypto 与前端 Worker + hash-wasm 摘要模块已实现并完成本地验证。业务判等与去重范围仍待确认，完整去重未实施。
> 日期：2026-10-15。
> 关联设计：[上传改造设计方案](./设计方案.md)。

## 1. 背景与目标

当前上传模块按用户和 `clientUploadId` 复用同一上传会话，新会话生成新的 MinIO 对象 Key。本次已接入完整内容摘要；尚无独立物理文件表或长期业务文件表，不同会话上传相同内容仍可能保存多个对象。

用户提出的目标：相同内容只保留一份最终 MinIO 对象；文件名、企业／项目归属及其他业务信息独立保存，多条业务记录可以引用同一份内容。

“最终只存一份”允许上传中、并发上传或失败恢复期间存在临时副本；完成去重和补偿清理后，只保留一份有效内容。本次先实现完整摘要计算与上传完成恢复，为后续内容去重提供可信依据。

## 2. 业务规则

| 文件内容 | 当前业务范围内的文件信息                   | 结果                                           |
| -------- | ------------------------------------------ | ---------------------------------------------- |
| 尚不存在 | 任意                                       | 保存内容，建立物理文件记录和业务文件记录       |
| 已存在   | 与已有有效业务记录相同                     | 返回已有业务文件记录，不新增业务记录或最终对象 |
| 已存在   | 与已有业务记录不同，或该范围内没有业务记录 | 只新增业务文件记录，引用已有物理文件           |

“内容相同”指完整文件原始字节相同。文件名、大小、修改时间、客户端摘要或分片 ETag 不能单独证明内容相同。设计建议采用服务端验证的完整 SHA-256 与实际字节数识别内容。

“文件信息相同”需要确定判等字段和业务范围。不能先把规则缩减为“文件名相同”，也不能把每次变化的创建时间纳入判等。同一内容的两个不同名字可以产生不同业务文件 ID，并引用同一物理文件 ID。

## 3. 范围与上传路径

包含分片上传兼容、内容识别、业务判等、对象复用、并发防重、失败恢复、下载名和引用回收。暂不实施历史对象合并，不因本轮讨论确定公开／私有下载策略。

### 3.1 上传后校验与去重

该路径可以在不增加前端完整摘要计算的情况下实现目标：

1. 校验上传者及目标业务范围权限，规范化业务文件信息，建立或恢复上传会话。
2. 沿用分片上传、重传和断点续传，合并得到候选完整对象。
3. 服务端按原始字节顺序流式计算完整 SHA-256，校验实际大小。
4. 在去重范围内查找或建立物理文件，再按业务信息查找或建立业务文件。
5. 固化会话完成结果，返回对应业务文件；清理重复候选对象。

此路径中的重复内容仍需要上传，收益是最终存储去重，不能称为上传前秒传。

### 3.2 上传前查询与复用（可选）

只有需要上传前避免传输时，才增加前端预计算与复用查询：

1. 前端先读取完整本地文件，计算候选摘要。
2. 服务端检查当前用户可访问的业务范围、可复用内容及持有验证条件。
3. 满足可信复用条件时，返回已有业务记录或新增业务引用。
4. 条件不满足时继续正常上传，并走服务端完整校验。

客户端仅报出 SHA-256 不能取得任意已有文件的引用、下载 URL 或权限。跨用户／跨企业秒传是否支持及持有证明策略待确认。边上传边计算可以重叠工作，但不能据此承诺在上传开始前完成完整摘要查询。

## 4. 摘要执行与前端实现

服务端确定使用 Node.js 原生 `crypto.createHash('sha256')`，不引入 Rust。合并后顺序流式读取完整对象，校验实际字节数，摘要与完成状态一起持久化。分片上传仍拒绝空文件。

`hash.update()` 是同步 CPU 工作；本次采用 Node Worker 线程执行摘要，主线程按背压逐块传送字节，限制同时计算数量并设置超时。线程隔离不免除同机 CPU、内存和存储带宽竞争。

服务端在完成请求内等待校验，不引入持久化队列。失败后保留 `completing`，后续完成请求从完整对象重新验证；已完成请求复用持久化结果。详细状态、错误和兼容规则见[技术契约](./技术契约.md)。长耗时的后台调度仍可在实测后独立引入。

本次不建立物理／业务文件表，不实现秒传、重复对象合并或引用回收；这些能力依赖尚待确认的业务判等和权限范围。

用户已确认前端采用 Web Worker + 现成增量 SHA-256 库 `hash-wasm`，不自建 Rust 内核。当前前端没有上传页面或调用入口，本轮交付可供上传流程调用的本地模块，不另建业务页面或秒传接口。Worker 顺序读取默认 4 MiB 的小块，提供进度、取消及资源释放；每个页面模块实例最多同时运行两个任务，其余等待，等待任务也可取消。

前端模块须通过标准向量、二进制与分块边界、空输入内核、取消与失败释放、浏览器真实 Worker 和生产打包验证。前端摘要仅为候选值，不能替代服务端校验，也不能凭摘要获得已有文件权限。真实 90 GiB 性能另行实测。

## 5. 权限与数据约束

- 业务记录复用限定在用户有权访问的范围内；存储复用不继承其他用户、企业或项目的业务权限。
- 去重范围是否全局、按企业或按其他存储域隔离待确认；公开／私有访问策略不能因内容相同而被无条件合并。
- 物理内容不可变，文件名和业务归属保存在业务记录中；下载名根据所访问的业务文件生成。
- 完整 SHA-256 按原始字节顺序对同一实例增量计算；不能拼接各分片摘要获得完整文件摘要。MinIO Multipart ETag 不作为完整文件 MD5 或 SHA-256。
- 建议物理层和业务层分别建立并发唯一约束。判等需明确空值、大小写、空白、软删除及上传人的作用。
- 未验证候选对象不能进入可复用内容集合。重复候选、失败对象和未完成分片需要独立的补偿清理。
- 删除业务文件只解除相应引用；无仍需保留的引用后才能回收物理对象。回收与新建引用必须有并发保护。
- 会话取消／过期清理不得删除已被业务文件引用的共享对象。

## 6. 验收标准（待实施）

1. 首次上传产生一份最终对象和一条业务记录。
2. 同业务范围、同内容、同信息重复上传，返回相同业务文件 ID，最终对象数和业务记录数不增加。
3. 同内容使用不同名字，业务文件 ID 不同，物理文件 ID 相同，最终对象数不增加。
4. 同名不同内容不能命中内容去重；空文件和二进制文件也按字节内容处理。
5. 并发同内容上传收敛到一份有效物理内容；同业务信息的并发请求只形成一条有效业务记录。
6. 任意分片顺序、重传及续传后，最终摘要与完整原文件一致；不同读取块大小不影响结果。
7. 前后端摘要实现对相同字节结果一致，大文件计算内存有界，不阻塞页面交互或 NestJS 事件循环。
8. 摘要不符、实际大小错误、进程失败或取消不会把内容发布为可用；合并成功与验证成功有独立状态。
9. 进程退出、服务重启、合并成功但数据库失败、完成请求重试均能恢复，并返回同一完成结果。
10. 未授权请求和仅知道摘要的请求不能取得其他范围的业务记录或内容。
11. 删除一个引用不影响其他引用；无引用回收与新引用创建并发时不会产生失效引用；下载名字对应当前业务记录。
12. 若采用后台任务，前端能够查询校验中、失败和完成结果；若采用请求内等待，超时后的重试仍可恢复。
13. 性能报告覆盖代表性大小、并发、CPU、内存、存储读取、页面响应与总耗时；若增加 WASM，需覆盖加载和复制成本。

完整业务去重验收仍待实施。本次已验证前后端摘要基础能力、前端生产构建的真实 Worker／取消／并发控制，以及服务端完成恢复与 1 GiB 生成流；不代表真实 MinIO 或 90 GiB 性能已验证，见[测试报告](./测试报告.md)。

## 7. 待确认事项

1. “文件信息相同”的字段：文件名、企业、项目、用途、上传人及其他业务信息如何参与判等。
2. 内容去重范围与可见性隔离；是否支持公司级文件，`projectId` 是否可以为空。
3. 是否要求上传前秒传，以及允许的授权范围和持有验证方式。
4. 根据真实文件与并发实测，是否把本次请求内等待改为持久化后台调度。
5. 前端摘要在后续上传流程中的调用时机：上传前预计算还是与上传重叠；本轮只提供可调用模块。
6. 改名遇到已有同信息记录如何处理；软删除后重复上传是恢复还是新增。
7. 无引用保留时间、取消／超时规则、重试策略、资源并发限制，以及历史内容是否迁移。
8. 下载是否公开及 URL、缓存、撤回策略；这些选择不由存储去重自动决定。
