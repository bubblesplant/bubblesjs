# 上传文件内容去重与业务引用

> 状态：待确认；本轮记录用户提出的讨论方向，尚未实施。
> 日期：2026-10-14。
> 关联设计：[上传改造设计方案](./设计方案.md)。

## 1. 背景与目标

当前上传模块按用户和 `clientUploadId` 复用同一上传会话，新会话使用新的对象 Key。代码没有计算完整文件内容摘要，也没有独立的物理文件表与业务文件表，因此不同会话上传相同内容仍可能保存多个 MinIO 对象。

本轮讨论目标：相同文件内容只保留一份最终存储对象；文件名、业务归属及其他业务信息独立保存，多条业务记录可以引用同一份内容。

该目标扩展原上传改造讨论稿。现有分片上传行为不因文档更新发生变化，本文不代表已完成改造或已确定全部实施细节。

## 2. 讨论中的业务规则

| 文件内容 | 当前业务范围内的文件信息                   | 预期结果                                             |
| -------- | ------------------------------------------ | ---------------------------------------------------- |
| 尚不存在 | 任意                                       | 上传文件内容，建立物理文件记录及业务文件记录         |
| 已存在   | 与已有有效业务记录相同                     | 返回已有业务文件记录，不新增业务记录或最终对象       |
| 已存在   | 与已有业务记录不同，或该范围内没有业务记录 | 只新增业务文件记录，引用已有物理文件，不新增最终对象 |

“相同内容”表示完整文件字节相同，不以文件名、文件大小、修改时间或分片 ETag 判定。“相同文件信息”的字段集合尚待确认，不能仅凭文件名相同就返回已有记录。

文件名变化不修改共享物理文件；两个不同名字可以对应不同业务文件 ID，并引用同一个物理文件 ID。

## 3. 范围与关键流程

讨论范围包含内容识别、业务记录判等、对象复用、分片上传兼容、并发防重和引用删除。暂不实施业务代码、数据库迁移或历史对象合并，也不调整现有公开／私有下载决策。

候选流程：

1. 校验用户及目标业务范围的权限，规范化参与判等的文件信息。
2. 取得可信的完整内容标识，在约定的去重范围内查找已验证且可复用的物理文件。
3. 命中内容且命中相同有效业务记录时，返回当前用户有权使用的已有业务文件信息。
4. 命中内容但业务信息不同，在事务中新增业务文件记录并引用该物理文件。
5. 未命中内容，继续分片上传；内容校验完成后确定物理文件，并创建或复用业务文件记录。

初始化前避免再次传输文件字节属于“秒传”能力，不能仅因客户端报出的摘要存在就授予文件引用或读取权限。可信内容标识和持有证明策略未确定前，不承诺跨用户秒传。

2026-10-14 补充讨论方向：用户提出新增 Rust 程序，由 NestJS 调用，专门执行服务端文件摘要计算；前端考虑 Web Worker 配合 WebAssembly。调用方式、任务调度、前端实现及性能收益仍待评估，本轮只讨论和归档，不创建程序或修改上传流程。

## 4. 权限与数据约束

- 业务记录复用必须限定在用户有权访问的业务范围内。物理存储复用不继承其他用户、公司或项目的业务权限。
- 去重范围是否全局、按企业或按其他存储域隔离仍待确认；不同公开／私有策略不能因相同内容被无条件合并。
- 物理文件内容不可变。文件名、描述、业务归属和业务用途保存在业务记录中；具体字段集合待确认。
- 建议以服务端验证的完整 SHA-256 摘要和字节数识别内容，并为去重范围内的物理文件建立唯一约束。MinIO Multipart ETag 不作为完整文件摘要。
- 业务记录需要独立的判等约束，并明确空值、大小写、空白、软删除记录及上传人是否参与判等；不使用每次变化的创建时间判等。
- 多个上传并发命中同一内容时，最终只能形成一条物理文件记录及一个有效最终对象；临时分片／对象允许存在，但必须有补偿清理流程。
- 删除一条业务记录只解除该业务引用。物理对象必须在没有仍需保留的引用后才能进入回收流程，回收期间需要防止与新增引用竞争。
- 未完成分片的取消／过期清理与共享最终对象回收属于不同流程，不能混用。

## 5. 验收标准（待实施）

1. 首次上传内容，产生一份最终对象和一条业务记录。
2. 同一业务范围重复上传同一内容且相同文件信息，返回相同业务文件 ID，业务记录数和最终对象数均不增加。
3. 同一内容使用不同名字，产生不同业务文件 ID，但物理文件 ID 相同，最终对象数不增加。
4. 同名但内容不同的文件，不能命中内容去重。
5. 不同业务范围或无访问权限的请求，不能直接得到其他范围的业务记录，也不能仅靠摘要取得其他用户文件内容。
6. 并发上传相同内容能够收敛到单个有效最终对象；同业务信息的并发请求只保留一条有效业务记录。
7. 删除一个引用不会影响剩余引用；无引用回收与新引用创建并发时不会产生失效引用。
8. 内容摘要校验失败不会把错误内容登记为可复用物理文件。
9. 后续若采用 Rust／WebAssembly，前后端对相同字节、不同读取块大小都应产生相同完整 SHA-256；大文件计算保持内存有界，取消及失败不会发布未经校验的内容。
10. 后续若使用后台摘要任务，接口不能把“MinIO 合并成功”直接表示为“内容验证通过”；验证中、验证失败及可用结果需有清晰状态，具体契约待确定。

以上为后续验收目标，本轮只进行源码核对和文档归档，未执行这些场景的实现测试。

## 6. 待确认事项

1. “文件信息”具体包含哪些字段；企业、项目、业务用途、上传人是否参与判等。
2. 内容去重是全局还是按企业／其他存储域隔离，以及不同可见性的隔离规则。
3. 是否要求上传前秒传；若要求，服务端如何验证客户端确实持有内容。
4. 文件改名是否只更新当前记录；软删除后再次上传是恢复还是新增记录。
5. 无引用物理文件的保留时间，以及历史重复对象是否纳入迁移。
6. 服务端是否采用 Rust 子进程；摘要任务是否通过独立队列／Worker 调度，以及超时、取消、资源限制和失败重试策略。
7. 前端是否需要预先计算摘要，以及采用已有增量 SHA-256 WebAssembly 库还是复用自建 Rust 内核；前端／后端方案需实测后再确定。
