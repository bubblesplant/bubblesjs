# 数据库迁移指南（Drizzle + PostgreSQL）

> 适用目录：`packages/create-bubbles/template-vp-monorepo-react-nestjs`
>
> 适用技术栈：NestJS 11、Drizzle ORM、drizzle-kit、PostgreSQL 18、pnpm monorepo。
>
> 本文面向以前端开发为主、刚开始写 NestJS 的开发者。请按顺序操作，修改表结构后不要忘记生成并提交迁移文件。

## 一、迁移体系一览

本平台不使用 TypeORM，数据库表结构由 **Drizzle ORM** 的 schema 文件定义，再由 **drizzle-kit** 编译成有序的 SQL 迁移文件。

| 项                         | 位置                                                                              | 说明                                                                                                     |
| -------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 表结构定义（唯一事实来源） | `apps/server/src/database/schema.ts`、`apps/server/src/database/access.schema.ts`、`apps/server/src/database/organization.schema.ts` | 所有表、字段、枚举、索引都在这里声明                                                                     |
| 迁移工具配置               | `apps/server/drizzle.config.ts`                                                   | 指定 schema 路径、迁移输出目录、数据库方言（postgresql）和连接串                                         |
| 已生成的迁移 SQL           | `apps/server/drizzle/`                                                            | 形如 `0000_xxx.sql`、`0001_xxx.sql` 的版本文件                                                           |
| 迁移快照与链路             | `apps/server/drizzle/meta/`                                                       | `_journal.json` 和各版本 snapshot，记录迁移先后顺序，**必须随迁移文件一起提交**                          |
| 应用侧连接配置             | `apps/server/src/config/database.config.ts`                                       | NestJS 启动时读取 `DB_*` 环境变量创建连接池                                                              |
| 环境变量                   | `apps/server/.env.development`（及 `.env.production`）                            | `DATABASE_URL` 供 drizzle-kit 使用，`DB_*` 供运行时使用                                                  |
| PostgreSQL 服务            | 根目录 `docker-compose.yml`                                                       | `postgres:18-alpine`，容器名 `vp-postgres`，端口 5432，账号/密码/库名均为 `postgres` / `ml` / `postgres` |

环境变量加载顺序见 `apps/server/src/utils/env-arr.ts`：`.env.${NODE_ENV}.local` → `.env.local` → `.env.${NODE_ENV}` → `.env`，本地覆盖文件不要提交。

## 二、相关 npm 脚本

脚本定义在 `apps/server/package.json`，均需在 `apps/server` 目录下执行：

| 命令                                | 作用                                          | 使用场景                           |
| ----------------------------------- | --------------------------------------------- | ---------------------------------- |
| `pnpm db:generate`                  | 对比 schema 与最新快照，生成新的迁移 SQL 文件 | 修改 schema 之后                   |
| `pnpm db:migrate`                   | 把 `drizzle/` 中尚未执行的迁移应用到数据库    | 首次拉代码、切换分支、部署时       |
| `pnpm db:push`                      | 跳过迁移文件，直接把 schema 硬同步到数据库    | **仅限本地快速调试**，不留版本记录 |
| `pnpm db:studio`                    | 启动 Drizzle Studio 网页端查看/编辑数据       | 本地排查数据                       |
| `pnpm access:init --account <账号>` | 写入访问控制（角色、权限等）种子数据          | 迁移完成后的初始化                 |

## 三、标准迁移流程

### 1. 启动 PostgreSQL（在项目根目录）

```powershell
docker compose up -d postgres
```

如同时需要 Redis、MinIO，执行 `docker compose up -d` 启动全部服务。可用 `docker compose ps` 确认 `vp-postgres` 处于 running 状态。

### 2. 应用已有迁移（首次拉代码或切分支后必做）

```powershell
cd apps/server
pnpm db:migrate
```

该命令会读取 `apps/server/.env.development` 中的 `DATABASE_URL`（当前为 `postgresql://postgres:ml@localhost:5432/postgres`），自动跳过已执行的迁移，只执行新增部分。

### 3. 修改 schema

在 `src/database/schema.ts`、`src/database/access.schema.ts` 或 `src/database/organization.schema.ts` 中新增表、字段、索引或枚举，并按现有领域边界选择对应文件。

### 4. 生成迁移文件

```powershell
pnpm db:generate
```

执行后会在 `apps/server/drizzle/` 下生成新文件，例如 `0003_xxx.sql`，同时更新 `drizzle/meta/` 快照。

**生成后必须打开 SQL 文件人工检查一遍**，重点确认：

- 删列、改类型等操作是否会丢数据；
- 新增非空列是否提供了默认值；
- 索引、约束名称是否符合预期。

### 5. 应用迁移

```powershell
pnpm db:migrate
```

### 6. 提交到 Git

迁移 SQL 与 `drizzle/meta/` 目录要**一起提交**。其他同学或部署环境拉到代码后，执行 `pnpm db:migrate` 即可得到完全一致的表结构。

### 7.（可选）初始化权限种子数据

```powershell
pnpm access:init --account <已注册的完整账号>
```

该命令由 `src/access-init.ts` 驱动，为指定账号写入企业访问控制所需的角色、权限等基础数据。

一句话总结工作流：

```text
改 schema.ts → pnpm db:generate → 检查 SQL → 连同 meta 一起提交 → 各环境 pnpm db:migrate
```

## 四、generate 与 push 的区别

- **`db:generate` + `db:migrate`**：正式流程。迁移有历史、可审查、可在各环境按顺序重放，团队协作和生产环境只能用这条路。
- **`db:push`**：直接比对 schema 后硬改数据库，速度快但不生成迁移文件，遇到删列等操作可能直接丢数据。仅允许在本地草稿/演示阶段使用，**不要对共享数据库或生产库使用**。

## 五、注意事项

1. **不要改名或删除已有迁移文件**。drizzle-kit 在数据库中维护迁移记录表，靠文件名和 `meta/_journal.json` 判定执行状态；改动历史文件会导致迁移链断裂，后续 `migrate` 报错。
2. **迁移文件和 `meta/` 快照必须一起提交**，只提交 SQL 不提交快照会让其他人生成的下一个迁移与当前状态对不上。
3. **一个迁移只做一件事**，避免在一个 SQL 文件里混合大量无关变更，方便审查和定位问题。
4. **数据库连不上时先查基础设施**：Docker 是否启动（`docker compose ps`）、5432 端口是否被占用、`.env` 中账号密码是否与 `docker-compose.yml` 一致。
5. 生产环境的连接串通过 `.env.production` 或部署平台的环境变量注入，不要把真实密码写进仓库。

## 六、更换数据库 / 数据备份与搬迁

迁移 SQL 只负责**表结构**，不负责搬运业务数据。

### 1. 先看懂连接串

`DATABASE_URL` 的格式固定如下，`@` 用于分隔"账号信息"和"服务器地址"：

```text
postgresql://用户名:密码@主机地址:端口/库名
```

本项目开发环境的实际值（见 `apps/server/.env.development`）：

```text
postgresql://postgres:ml@localhost:5432/postgres
└── 协议          └用户  └密码 └主机     └端口 └库名
```

主机地址按部署位置填写：

| 数据库位置                       | 主机地址填什么             | 示例                                                    |
| -------------------------------- | -------------------------- | ------------------------------------------------------- |
| 本机（含本机 Docker 映射的端口） | `localhost` 或 `127.0.0.1` | `postgresql://postgres:ml@localhost:5432/postgres`      |
| 局域网内另一台服务器             | 那台机器的内网 IP          | `postgresql://postgres:ml@192.168.1.50:5432/postgres`   |
| 云数据库 / 有域名                | 服务商提供的域名           | `postgresql://postgres:ml@db.example.com:5432/postgres` |

### 2. 仅更换连接地址（目标库是空库）

适用于"换一台数据库服务器，但不需要搬旧数据"的场景：

1. 修改目标环境的 `DATABASE_URL` 与 `DB_HOST`、`DB_PORT`、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`（本地调试可放到不提交的 `.env.development.local`）；
2. 确保目标数据库**已被创建**（容器版默认只有 `postgres` 库；换库名需先建库）；
3. 在目标环境执行 `pnpm db:migrate` 建好全部表结构；
4. 需要时执行 `pnpm access:init --account <账号>` 初始化种子数据。

### 3. 备份与整体搬迁（表结构 + 业务数据）

使用 PostgreSQL 原生的 `pg_dump` / `pg_restore` 最稳妥。

> **敏感备份警告：** `.spaces/05.运行维护/数据库迁移/备份/backup.dump` 是数据库二进制快照，可能包含账号、成员关系和其他业务数据。仓库内只允许保留确认过的本地虚构或已脱敏开发数据；严禁把生产、客户或未经脱敏的备份提交到版本库。导出新备份后，应先核对数据来源和敏感性，再决定是否留存；本指南不授权删除当前快照。

> ⚠️ 本项目的 PostgreSQL 跑在 Docker 容器 `vp-postgres` 中，**Windows 宿主机上通常没有安装 `pg_dump`**，直接在 PowerShell 执行会提示"不是内部或外部命令"。
> 因此统一通过 `docker exec` 在容器内执行，并用 `docker cp` 把备份文件拷进/拷出容器。
> 以下命令均在**项目根目录**（`docker-compose.yml` 所在目录）执行。

**备份（导出）**：

```powershell
# 1. 在容器内把整个 postgres 库导出为压缩备份（容器内本地连接无需输密码）
docker exec vp-postgres pg_dump -Fc -U postgres -d postgres -f /var/lib/postgresql/backup.dump

# 2. 把备份文件从容器拷到当前目录
docker cp vp-postgres:/var/lib/postgresql/backup.dump ./backup.dump
```

参数说明：`-Fc` 表示 custom 自定义压缩二进制格式，体积小、可选择性恢复，必须配合 `pg_restore` 使用；`-f` 指定输出文件路径。

**恢复（导入）**：

```powershell
# 1. 把备份文件拷进容器
docker cp ./backup.dump vp-postgres:/var/lib/postgresql/backup.dump

# 2. 在容器内恢复到 postgres 库（--clean 先删除同名旧对象，--if-exists 避免对象不存在时报错）
docker exec vp-postgres pg_restore -U postgres -d postgres --clean --if-exists /var/lib/postgresql/backup.dump
```

建议备份文件名带上日期，避免多次备份互相覆盖，例如 `backup-20260912.dump`。

**搬迁到另一台服务器**时：在旧服务器按上面"备份"两步拿到 dump 文件，传送到新服务器后：

- 若新服务器也是同样的 Docker 部署，按上面"恢复"两步操作即可；
- 若新服务器是本机安装的 PostgreSQL 且已安装客户端工具，可直接用连接串恢复，例如：

  ```powershell
  pg_restore -d "postgresql://postgres:ml@192.168.1.50:5432/postgres" --clean --if-exists backup.dump
  ```

搬迁完成后，把应用的环境变量指向新库并启动验证即可，**无需再跑 `db:migrate`**——表结构、数据以及 drizzle 的迁移记录表都已随 dump 一起恢复。

> 版本提示：`pg_dump` 的大版本不应低于（最好等于）被导出的 PostgreSQL 版本。用容器内自带的工具天然与服务端版本一致，可避免版本不匹配的警告和兼容问题。

## 七、常见问题排查

| 现象                            | 可能原因                                                    | 处理                                                                            |
| ------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `DATABASE_URL 未配置`           | drizzle-kit 没读到 env 文件                                 | 确认在 `apps/server` 下执行，且 `.env.development` 存在；检查 `NODE_ENV`        |
| `ECONNREFUSED 127.0.0.1:5432`   | PostgreSQL 容器未启动                                       | 根目录执行 `docker compose up -d postgres`                                      |
| `database "xxx" does not exist` | 连接串中的库名与实际不符                                    | 以 `docker-compose.yml` 中的 `POSTGRES_DB` 为准，或手动 `CREATE DATABASE`       |
| `pg_dump 不是内部或外部命令`    | 宿主机未安装 PostgreSQL 客户端工具                          | 用 `docker exec vp-postgres pg_dump ...` 在容器内执行（见第六节）               |
| migrate 报迁移历史不一致        | 历史迁移文件或 meta 被改动                                  | 恢复被删改的文件；必要时在开发库清理 drizzle 迁移记录表后重新迁移（仅限开发库） |
| generate 生成了意料之外的 DROP  | 快照与 schema 差异过大（如重命名列会被识别成删旧列+加新列） | 放弃生成，改用手写迁移或先保留旧列做数据过渡                                    |

## 八、涉及的后端知识点

- **Schema 迁移（migration）的本质**：把"表结构长什么样"从代码编译成有序、可追溯、可在各环境重放的 SQL 版本文件，解决多人协作与多环境下表结构不一致的问题，作用类似前端的 lock 文件——人人按同一份脚本得到相同结果。
- **迁移记录表**：`db:migrate` 会在库中维护一张迁移日志表，记录哪些迁移文件已执行，保证每个迁移只执行一次。这就是迁移文件不能随意改名或删除的原因。
- **代码即结构（schema-as-code）**：Drizzle 的 schema 既是建表依据，也是 TypeScript 类型和查询 API 的来源，改结构 = 改代码，天然可走 Code Review 和版本管理流程。
