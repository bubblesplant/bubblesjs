# `.spaces` 文档规范

## 1. 目的和适用范围

本规范适用于项目中的需求、澄清、PRD、设计、技术契约、UI 原型与截图、测试证据、联调记录、交付说明和运行文档。`.spaces/` 是上述内容的唯一正式来源，`artifacts/` 不再作为产物目录使用。

## 2. 目录组织

```text
.spaces/
├── README.md
├── 文档规范.md
└── <序号>.<业务主题>/
    └── <功能>/
        ├── 需求文档.md
        ├── PRD.md
        ├── 设计方案.md
        ├── 技术契约.md
        ├── 决策记录.md
        ├── 联调记录.md
        ├── 测试报告.md
        ├── ui/
        ├── 测试证据/
        └── 工具/
```

- 一级目录使用 `<两位序号>.<主题>`，序号只用于稳定排序，不表达优先级。
- 新增、移动、合并或重命名一级主题与主要功能目录时，必须同步更新根目录 `README.md` 的索引、状态和相关决策链接。
- 一个功能只有一个文件时，可以直接放在主题目录；同一功能出现两个或以上文件或产物时，必须建立功能子目录。
- 同一功能不得同时散落在多个主题。跨主题只使用相对链接引用，不复制正文。
- 不建立含义模糊的 `todo/`、`temp/`、`new/`、`final/` 目录。待确认事项写入所属需求或设计文档。

## 3. 文档职责

| 文档 | 负责内容 | 不应包含 |
| --- | --- | --- |
| `需求文档.md` | 背景、目标、范围、业务规则、权限边界、数据约束、验收标准、待确认项 | 未确认的接口和数据库细节 |
| `PRD.md` | 用户故事、页面／流程、验收映射 | 与需求文档冲突的第二套业务规则 |
| `设计方案.md` | 领域模型、交互、架构取舍、替代方案和边界 | 冒充当前实现的历史设想 |
| `技术契约.md` | DTO、接口、错误、权限、数据约束、兼容与迁移规则 | 前后端各自维护的重复类型 |
| `决策记录.md` | 跨轮次重要结论的日期、状态、原因、影响范围和正式文档链接 | 原始聊天全文或另一套需求正文 |
| `联调记录.md` | 实际联调范围、发现、修复和遗留项 | 未执行却声称通过的结论 |
| `测试报告.md` | 环境、版本、执行证据、结果、未覆盖风险 | 仅依据代码阅读得出的“已通过” |

文档应尽量引用权威来源。需要摘要时标明“摘要”，并附相对链接。

## 4. 新需求和需求变更

1. 收到新需求、需求澄清或变更时，先定位所属主题和功能；没有目录时先建立目录，再开始实现。
2. 新需求至少记录目标、范围、业务规则、权限边界、数据约束、验收标准和待确认项。
3. 需求变更直接修改原文档中的现行结论，并同步所有受影响的 PRD、设计、契约、UI、测试和运行说明。
4. 原文档维护“变更记录”，至少写日期、摘要、影响范围和决策原因。版本历史交给 Git，不创建 `v2`、`最终版`、`最新版` 等正文副本。
5. 新结论推翻旧结论时，删除旧的现行表述，或明确标为“已废弃／历史基线”；不得在同一文档中保留两套互相矛盾的当前规则。
6. 尚未确认或尚未实现的内容必须标注状态。未经用户确认的讨论方向不得写成有效需求。

## 5. 产物归档

- UI 原型、截图和标注图放在所属功能的 `ui/`。
- 自动化测试结果、JSON 报告和不可读性较强的原始证据放在 `测试证据/`，并由测试报告解释其含义。
- 为生成或验证产物保留的脚本放在 `工具/`，输出路径必须指向同一功能目录，不得重新生成 `artifacts/`。
- 运行说明、联调记录和测试报告放在产生它们的功能目录；全局运维文档放在 `05.运行维护/`。
- 二进制备份、数据库转储等材料即使位于 `.spaces/`，也必须按敏感数据管理，不得默认视为可公开文档。

## 6. 状态和证据

文档开头应明确状态，推荐使用以下值：

- `当前有效`：已确认，且作为当前实现或实施依据。
- `待实施`：需求或方案已确认，但实现尚未完成。
- `待确认`：仍有会改变结果的产品或技术选择。
- `历史基线`：只用于追溯，不能作为当前实现依据。
- `验证记录`：记录某一时间点和版本的执行结果，不自动覆盖后续变更。

需求变化使既有测试失效时，必须把受影响项目标为“待重验”或“历史证据”。只有重新执行后才能恢复“通过”。

## 7. 从会话和临时资料整理文档

- 只提炼稳定决策、业务规则、设计取舍、接口约束和待确认项，不保存原始聊天流水。
- 同一主题存在多次讨论时，按最新明确决定覆盖旧结论；无法判断是否确认时写入“待确认事项”。
- 跨轮次且容易反复影响范围的结论可以维护 `决策记录.md`，但只作为索引；现行规则仍必须落入需求、设计或技术契约。
- 对话中的示例账号、请求头、Cookie、Token、密钥、连接串和生产数据必须丢弃或脱敏。
- 已在正式文档存在的内容只更新原文档，不另建“对话总结”副本。
- 整理完成后检查代码、契约、测试报告和运行说明是否仍引用旧结论。

## 8. 链接、命名和提交检查

- 仓库内 Markdown 使用相对链接；移动文件后同步修复全部引用。
- `.spaces/README.md` 维护主题与主要功能的导航；目录结构变化后必须同步更新，避免出现只有文件归档、没有入口索引的孤立产物。
- 文件名使用稳定业务含义，不包含日期、人员名或阶段后缀。
- 提交前至少检查：旧路径、失效链接、重复正文、`artifacts/` 残留、敏感信息、过时状态、未同步契约和测试结论。
- 需求或契约涉及代码实现时，按项目 `AGENTS.md` 的按需规则继续读取代码设计和共享代码规则。
