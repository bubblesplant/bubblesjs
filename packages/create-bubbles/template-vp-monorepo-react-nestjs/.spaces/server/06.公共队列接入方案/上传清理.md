# 上传清理接入公共队列（附加方案）

> 状态：未来附加项，当前不实施  
> 前置方案：[公共队列接入方案](./README.md)

## 0. 结论先行

上传清理以后直接复用公共队列，不再新建一套 Redis、Queue Service 或 Worker 基础设施。

第一版建议只增加一个“处理单个上传会话”的任务：

```text
upload.multipart-expire.v1
```

如果以后决定把“结果不确定的 completing 会话恢复”拆成独立协议，再增加：

```text
upload.session-reconcile.v1
```

不要第一天就同时实现两个任务。先确定上传状态机和职责边界；第一版可以只实现过期回收，再根据实际故障恢复需求决定是否拆出 reconcile 任务。

任务 Payload 只传：

```json
{
  "uploadSessionId": "上传会话 UUID"
}
```

不要把 Bucket、Object Key、MinIO UploadId、Access Key 或 Secret 放进队列 Payload。Worker 必须根据 uploadSessionId 重新读取数据库，取得可信的存储信息。

整体关系如下：

```text
未来的定时触发器或运维命令
          │
          │ 查询待清理会话 ID
          ▼
TaskQueueService.enqueue(...)
          │
          ▼
BullMQ: server-tasks
          │
          ▼
TaskQueueProcessor
          │ Zod 校验 + 按 job.name 分发
          ▼
UploadCleanupHandler
          │
          ├── 重新读取数据库
          ├── 领取清理权并检查在途分片
          ├── 调用 MinIO Abort / Head 等操作
          └── 条件更新最终状态
```

这份文件只是未来接入蓝图，不代表上传清理已经完成，也不要求现在安装定时任务依赖。

---

## 1. 前端需要知道什么

前端不直接连接队列，也不负责触发后台过期扫描。

前端现有行为仍然是：

- 正常完成上传时调用 Complete 接口。
- 用户主动取消时先停止并等待在途分片请求结束，再调用取消接口。
- 页面关闭、断网或客户端崩溃后遗留的会话，由未来的后台清理任务兜底。

队列中的“上传清理”主要解决无人继续操作的过期会话和结果不确定的后台补偿，不替代前端正常的完成、暂停和取消流程。

---

## 2. 第一版任务边界

第一版只考虑：

- 接收一个 uploadSessionId。
- 重新读取上传会话。
- 判断是否确实需要清理或恢复。
- 幂等执行存储操作。
- 条件更新数据库状态。
- 失败时使用公共队列的重试和退避策略。

第一版暂不包含：

- 自动定时扫描实现。
- 扫描整个 MinIO Bucket 寻找孤儿 Multipart。
- Bull Board 管理页面。
- 前端任务进度页面。
- 删除已经完成的正式文件。
- 扩大 MinIO 运行时账号权限。

特别注意：上传清理只处理未完成 Multipart 或状态恢复。它不能把“清理过期上传”和“删除用户正式文件”混成同一个任务。

## 3. 任务协议

未来在 task-queue.constants.ts 中增加：

```ts
export const TASK_JOB_NAMES = {
  QUEUE_SMOKE: 'system.queue-smoke.v1',
  UPLOAD_MULTIPART_EXPIRE: 'upload.multipart-expire.v1',
} as const
```

在 task-queue.contracts.ts 中增加：

```ts
export const UploadMultipartExpirePayloadSchema = z.object({
  uploadSessionId: z.string().uuid(),
})

export interface TaskPayloadMap {
  [TASK_JOB_NAMES.QUEUE_SMOKE]: z.infer<typeof QueueSmokePayloadSchema>
  [TASK_JOB_NAMES.UPLOAD_MULTIPART_EXPIRE]: z.infer<typeof UploadMultipartExpirePayloadSchema>
}

export const TASK_PAYLOAD_SCHEMAS = {
  [TASK_JOB_NAMES.QUEUE_SMOKE]: QueueSmokePayloadSchema,
  [TASK_JOB_NAMES.UPLOAD_MULTIPART_EXPIRE]: UploadMultipartExpirePayloadSchema,
} satisfies Record<TaskName, z.ZodType>
```

任务名带 v1，是为了把它当成稳定协议。以后 Payload 或语义发生不兼容变化时，应新增 v2，不要静默改变旧任务的解释方式。

## 4. 如何投递

未来由上传领域内的 Service 负责找出需要处理的 uploadSessionId，再调用公共 TaskQueueService：

```ts
await this.taskQueue.enqueue(TASK_JOB_NAMES.UPLOAD_MULTIPART_EXPIRE, {
  uploadSessionId,
})
```

第一版可以先让 BullMQ 自动生成 jobId，把真正的并发互斥和幂等交给数据库 Claim。

如果以后需要用自定义 jobId 辅助去重，必须使用连字符，不能包含冒号，并建议加入数据库中的清理批次或 Claim UUID，例如：

```text
upload-multipart-expire-<uploadSessionId>-<cleanupClaimId>
```

不要长期只使用 uploadSessionId 作为 jobId。失败 Job 默认会保留一段时间，旧 Job 尚未删除时，再次 add 相同 jobId 不等于创建了一次新的补偿执行。

jobId 只能辅助削峰，不能代替数据库幂等；BullMQ 是至少一次执行，任务仍可能被重复处理。

扫描到一批会话时，应逐个投递小 Job，不要把成百上千个会话和内部存储字段塞进一个巨大 Payload。

## 5. 如何接入公共 Processor

仍然使用公共队列唯一的 TaskQueueProcessor，不为 server-tasks 再注册第二种互相竞争、却无法识别全部任务名的 Processor 类型。

未来在 switch 中增加：

```ts
case TASK_JOB_NAMES.UPLOAD_MULTIPART_EXPIRE: {
  const parsed = UploadMultipartExpirePayloadSchema.safeParse(job.data)

  if (!parsed.success) {
    throw new UnrecoverableError('Invalid payload for ' + job.name)
  }

  return this.uploadCleanupHandler.handle(parsed.data)
}
```

Processor 只负责：

- 根据 job.name 路由。
- 对 Payload 做 Zod 运行时校验。
- 把非法协议转换成 UnrecoverableError。
- 记录不包含敏感 Payload 的公共日志。
- 让可恢复异常继续抛出，由 BullMQ 重试。

真正的上传状态判断和 MinIO 操作放进 UploadCleanupHandler，不要让公共 Processor 变成一个巨大的业务文件。

---

## 6. Handler 必须遵守的执行顺序

UploadCleanupHandler 每次执行都按下面顺序处理：

1. 根据 uploadSessionId 重新读取数据库。
2. 会话不存在时按幂等结果结束并记录数据完整性告警，不根据 Payload 猜测 Bucket 或 UploadId。
3. 已经处于明确终态且存储清理已确认时，幂等返回。
4. 在短数据库事务中领取清理权，并重新检查状态、过期时间和有效分片租约。
5. 有在途分片时不要 Abort；释放本次领取权，延后再试。
6. 提交数据库事务后，再调用 MinIO Head、ListParts、Complete 或 Abort。
7. 根据存储端真实结果，在新的短事务中条件更新会话状态。
8. 只有本 Worker 仍持有 cleanupClaimId 时，才允许写入最终结果或下一次重试时间。

禁止拿着数据库事务或行锁等待 MinIO 网络请求，否则并发稍高就可能耗尽数据库连接池。

如果进程在 MinIO 操作成功后、数据库更新前崩溃，下次执行必须能通过 HeadObject、ListParts 或 NoSuchUpload 等结果恢复，而不是假设上一次一定失败。

## 7. 实现前必须先确定状态机

上传模块最终至少需要明确这些状态的含义：

| 状态       | 需要回答的问题                                 |
| ---------- | ---------------------------------------------- |
| uploading  | 是否已经超过 expiresAt，是否仍有有效分片租约？ |
| completing | MinIO 是否已经合并成功，只是数据库结果未写回？ |
| aborting   | Abort 是否已经成功，只是数据库结果未写回？     |
| completed  | 是否绝对禁止清理任务删除正式对象？             |
| aborted    | 是否已确认未完成 Multipart 被释放？            |
| expired    | 表示“发现过期”还是“已经完成存储清理”？         |

尤其要先统一 expired 和 aborted 的区别。如果 expired 只表示“已经过期但还没清理”，它就不能被当成最终成功状态；如果 expired 表示“已经完成过期回收”，则必须有可靠证据确认存储端已处理。

没有确定状态机前，不要直接编写清理 Worker。

## 8. 多实例、幂等和领取租约

公共队列和多个同构 Worker 实例可以并行运行，但上传清理仍需要数据库级领取机制。

建议未来在 upload_sessions 中增加等价字段：

```text
cleanupClaimId
cleanupLeaseUntil
nextCleanupAt
lastCleanupError
```

一次正确的领取过程是：

1. 在短事务中选出待处理记录。
2. 写入随机 cleanupClaimId 和有限时长的 cleanupLeaseUntil。
3. 立即提交事务。
4. 事务外执行 MinIO 请求。
5. 按 uploadSessionId + cleanupClaimId 条件更新结果。
6. Worker 崩溃后，租约过期才允许其他实例重新领取。

只依赖 BullMQ jobId 去重不够。Job 可能重试、锁可能失效、Worker 可能在完成后尚未确认，真实 Handler 必须能安全重复执行。

更完整的上传竞态、分片租约和生产安全说明，可参考 [04.upload.md 的“过期清理和生产安全”章节](../04.upload.md#第-18-步过期清理和生产安全)。

## 9. 哪些错误重试

| 情况                   | 建议处理                               |
| ---------------------- | -------------------------------------- |
| Payload 不是合法 UUID  | 抛 UnrecoverableError，不重试          |
| 会话不存在             | 作为幂等结果结束，并记录安全元数据     |
| 已完成或已确认清理     | 幂等返回                               |
| 仍有有效分片租约       | 延后处理，不强行 Abort                 |
| PostgreSQL 暂时不可用  | 抛出普通异常，让 BullMQ 重试           |
| MinIO 超时或临时不可用 | 抛出普通异常，让 BullMQ 重试           |
| NoSuchUpload           | 结合数据库状态和 HeadObject 做幂等恢复 |
| 凭据或 Bucket 配置错误 | 任务最终失败并告警，不能吞掉异常       |

公共默认 attempts 为 3 只能处理短暂故障。持续故障还需要监控、人工处理入口和后续补偿扫描。

## 10. 将来如何触发

清理任务最终需要一个触发器，但这与公共队列基础搭建分开决定。可选方案包括：

- NestJS Schedule。
- BullMQ Job Scheduler。
- Kubernetes CronJob。
- 外部运维平台定时调用内部命令或接口。

无论选择哪一种，触发器只负责按索引、小批量寻找候选 uploadSessionId 并投递任务，不负责在扫描事务里直接调用 MinIO。

当前阶段不安装调度依赖。等上传状态机、过期规则和部署方式确定后，再单独选择触发方案。

---

## 11. 存储侧还需要兜底

应用主动清理之外，生产 MinIO Bucket 还应配置“若干天后终止未完成 Multipart”的生命周期规则，作为应用崩溃或数据库记录损坏后的最后保险。

生命周期规则不能替代应用任务，因为它不会帮业务数据库恢复 completed、aborted、expired 等状态。应用任务也不能替代生命周期兜底，因为应用自身可能长期不可用。

配置生命周期时必须先读取并合并 Bucket 已有规则，不能用一份新配置覆盖其他数据保留策略。


这里的文件名是职责建议，不要求现在创建空文件。

### 12.1 避免模块循环依赖

真正给 TaskQueueProcessor 注入 UploadCleanupHandler 时，要避免形成下面的循环：

```text
TaskQueueModule 导入 UploadModule
       ↑                 │
       └─────────────────┘
       UploadModule 又导入 TaskQueueModule
```

不要用大量 forwardRef 掩盖职责问题。接入第一个真实业务 Handler 前，建议把组装关系拆成：

```text
TaskQueueModule
  ├── BullMQ 根配置
  ├── Queue 注册
  └── TaskQueueService

UploadModule
  ├── 导入 TaskQueueModule，用于投递
  └── 导出 UploadCleanupHandler

TaskQueueWorkerModule
  ├── 导入 TaskQueueModule
  ├── 导入 UploadModule
  └── 提供 QueueWorkerBootstrap 和唯一 TaskQueueProcessor
```

AppModule 负责导入 TaskQueueWorkerModule。这样上传业务可以投递任务，公共 Worker 也能调用上传 Handler，但 TaskQueueModule 本身不需要反向依赖 UploadModule。

## 13. 测试清单

未来至少覆盖：

- 非法 Payload 不重试。
- 会话不存在时幂等结束。
- 未过期会话不会被清理。
- 有效分片租约存在时不会 Abort。
- 相同 Job 重复执行仍安全。
- 两个 Worker 同时处理时只有一个持有有效 Claim。
- MinIO Abort 成功、数据库更新失败后能够恢复。
- MinIO 返回 NoSuchUpload 时能够正确对账。
- completing 状态会先检查最终对象，不会直接 Abort。
- completed 状态绝不会删除正式对象。
- 临时数据库或 MinIO 错误会按公共策略重试。
- 日志不包含 Bucket、Object Key、UploadId、凭据或完整 Payload。

真实联调需要 PostgreSQL、Redis 和 MinIO，不能只依赖 Mock。

## 14. 将来的实施顺序

等决定真正开发上传清理时，按下面顺序推进：

1. 先完成并验收公共队列 README 中的基础能力。
2. 确定上传状态机，特别是 expired 和 aborted 的语义。
3. 完成分片租约与 cleanup claim 的数据库设计。
4. 实现可独立测试的 UploadCleanupHandler。
5. 增加任务名、Payload Schema 和 Processor 分支。
6. 补单元测试以及 Redis、PostgreSQL、MinIO 联调测试。
7. 再选择并实现定时触发器。
8. 最后配置监控、告警和 MinIO 生命周期兜底。

当前只保留这份附加方案，不执行以上步骤。
