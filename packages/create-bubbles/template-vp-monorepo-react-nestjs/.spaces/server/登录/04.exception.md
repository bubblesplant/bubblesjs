# NestJS 全局统一异常处理改造指南

> 目标：成功响应继续交给现有的 `ResponseInterceptor`，失败响应交给全局 `ExceptionFilter`。业务代码只选择一个集中定义的错误，不再重复手写 `code`、`message` 和 HTTP 状态码。

本文适配当前项目的 NestJS 11、Fastify、nestjs-zod 和 Vite+。

## 1. 最终效果

当前鉴权 Guard 中存在这样的代码：

```ts
throw new UnauthorizedException({
  code: 'SESSION_TOKEN_MISSING',
  message: '缺少有效的登录 Token',
})
```

完成改造后，业务代码只需要写：

```ts
throw new AppException(AUTH_ERRORS.SESSION_TOKEN_MISSING)
```

客户端收到的 HTTP 状态仍然是正确的 `401`：

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json
```

响应体统一为：

```json
{
  "code": "SESSION_TOKEN_MISSING",
  "data": null,
  "message": "缺少有效的登录 Token"
}
```

这里需要区分两个概念：

- HTTP 状态码 `401` 表示请求未通过身份认证，供浏览器、网关、监控和请求库判断。
- 响应体中的 `code` 表示具体业务原因，供前端区分“没有 Token”和“Token 已失效”。

不要为了统一响应格式，把所有业务错误都改成 HTTP `200`。建议保持以下语义：

| 业务情况 | HTTP 状态 | 响应体 code |
| --- | ---: | --- |
| 没有携带 Token | 401 | `SESSION_TOKEN_MISSING` |
| Token 已失效 | 401 | `SESSION_INVALID` |
| 账号或密码错误 | 401 | `INVALID_CREDENTIALS` |
| 账号已存在 | 409 | `ACCOUNT_ALREADY_EXISTS` |
| 请求参数错误 | 400 | `VALIDATION_FAILED` |
| Redis 或依赖服务暂时不可用 | 503 | `SERVICE_UNAVAILABLE` |
| 未知服务端错误 | 500 | `INTERNAL_SERVER_ERROR` |

## 2. 改造后的职责划分

```text
Controller / Service / Guard
        ↓ 选择具体业务错误
AppException
        ↓ 携带 code、message、HTTP status
GlobalExceptionFilter
        ↓ 统一异常响应格式
HTTP 4xx / 5xx + { code, data, message }
```

成功和失败分别处理：

```text
ResponseInterceptor       处理成功响应
GlobalExceptionFilter     处理失败响应
```

不建议把成功响应和异常响应全部塞进同一个拦截器。

## 3. 创建统一业务异常

新建文件：

```text
apps/server/src/common/exceptions/app.exception.ts
```

写入：

```ts
import { HttpException, type HttpStatus } from '@nestjs/common'

export interface AppErrorDefinition {
  readonly code: string
  readonly message: string
  readonly status: HttpStatus
}

export class AppException extends HttpException {
  constructor(error: AppErrorDefinition) {
    super(
      {
        code: error.code,
        message: error.message,
      },
      error.status,
    )
  }
}
```

`AppErrorDefinition` 统一规定每个业务错误必须包含：

- `code`：稳定的业务错误标识，前端可以据此执行特殊逻辑。
- `message`：默认展示给用户的错误文案。
- `status`：真正返回的 HTTP 状态码。

`AppException` 只负责把错误定义转换成 NestJS 能识别的 `HttpException`。

## 4. 集中定义认证错误

新建文件：

```text
apps/server/src/modules/auth/auth.errors.ts
```

写入：

```ts
import type { AppErrorDefinition } from '@/common/exceptions/app.exception'
import { HttpStatus } from '@nestjs/common'

export const AUTH_ERRORS = {
  SESSION_TOKEN_MISSING: {
    code: 'SESSION_TOKEN_MISSING',
    message: '缺少有效的登录 Token',
    status: HttpStatus.UNAUTHORIZED,
  },

  SESSION_INVALID: {
    code: 'SESSION_INVALID',
    message: '登录已失效，请重新登录',
    status: HttpStatus.UNAUTHORIZED,
  },

  SESSION_USER_INVALID: {
    code: 'SESSION_USER_INVALID',
    message: '用户不存在或账号已不可用，请重新登录',
    status: HttpStatus.UNAUTHORIZED,
  },

  INVALID_CREDENTIALS: {
    code: 'INVALID_CREDENTIALS',
    message: '账号或密码错误',
    status: HttpStatus.UNAUTHORIZED,
  },

  ACCOUNT_ALREADY_EXISTS: {
    code: 'ACCOUNT_ALREADY_EXISTS',
    message: '账号已存在',
    status: HttpStatus.CONFLICT,
  },

  USER_SERVICE_UNAVAILABLE: {
    code: 'USER_SERVICE_UNAVAILABLE',
    message: '暂时无法获取用户信息，请稍后重试',
    status: HttpStatus.SERVICE_UNAVAILABLE,
  },
} as const satisfies Record<string, AppErrorDefinition>
```

使用 `satisfies Record<string, AppErrorDefinition>` 后，如果某个错误漏写 `code`、`message` 或 `status`，TypeScript 会直接报错。

错误定义建议按业务模块拆分：

```text
modules/auth/auth.errors.ts
modules/user/user.errors.ts
modules/company/company.errors.ts
```

不需要把整个项目的业务错误都堆进一个超大的文件。

## 5. 创建全局异常过滤器

新建文件：

```text
apps/server/src/common/filters/global-exception.filter.ts
```

写入：

```ts
import {
  Catch,
  HttpException,
  HttpStatus,
  Injectable,
  Logger,
  type ArgumentsHost,
  type ExceptionFilter,
} from '@nestjs/common'
import { HttpAdapterHost } from '@nestjs/core'
import { ZodSerializationException, ZodValidationException } from 'nestjs-zod'

interface ErrorResponse {
  code: number | string
  data: null
  message: string
}

@Catch()
@Injectable()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name)

  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse()
    const { httpAdapter } = this.adapterHost

    if (exception instanceof ZodValidationException) {
      httpAdapter.reply(
        response,
        {
          code: 'VALIDATION_FAILED',
          data: null,
          message: '请求参数校验失败',
        },
        HttpStatus.BAD_REQUEST,
      )
      return
    }

    if (exception instanceof ZodSerializationException) {
      this.logException(exception)

      httpAdapter.reply(
        response,
        {
          code: 'INTERNAL_SERVER_ERROR',
          data: null,
          message: '服务器内部错误',
        },
        HttpStatus.INTERNAL_SERVER_ERROR,
      )
      return
    }

    if (exception instanceof HttpException) {
      const status = exception.getStatus()

      if (status >= HttpStatus.INTERNAL_SERVER_ERROR) {
        this.logException(exception)
      }

      httpAdapter.reply(response, this.normalizeHttpException(exception), status)
      return
    }

    this.logException(exception)

    httpAdapter.reply(
      response,
      {
        code: 'INTERNAL_SERVER_ERROR',
        data: null,
        message: '服务器内部错误',
      },
      HttpStatus.INTERNAL_SERVER_ERROR,
    )
  }

  private normalizeHttpException(exception: HttpException): ErrorResponse {
    const status = exception.getStatus()
    const payload = exception.getResponse()

    if (typeof payload === 'string') {
      return {
        code: status,
        data: null,
        message: payload,
      }
    }

    const body = payload as Record<string, unknown>
    const code =
      typeof body.code === 'string' || typeof body.code === 'number' ? body.code : status

    return {
      code,
      data: null,
      message: this.normalizeMessage(body.message, exception.message),
    }
  }

  private normalizeMessage(value: unknown, fallback: string) {
    if (typeof value === 'string') {
      return value
    }

    if (Array.isArray(value)) {
      const messages = value.filter((item): item is string => typeof item === 'string')

      if (messages.length > 0) {
        return messages.join('；')
      }
    }

    return fallback || '请求失败'
  }

  private logException(exception: unknown) {
    if (exception instanceof Error) {
      this.logger.error(exception.message, exception.stack)
      return
    }

    this.logger.error(String(exception))
  }
}
```

### 5.1 为什么使用 HttpAdapterHost

当前项目通过 `FastifyAdapter` 启动 NestJS：

```ts
const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter(...),
)
```

因此异常过滤器不要使用 Express 专属的写法：

```ts
response.status(status).json(body)
```

通过 `HttpAdapterHost.httpAdapter.reply()` 返回响应，可以兼容当前的 Fastify，也不会把公共代码绑定到 Express。

### 5.2 过滤器的处理顺序

过滤器按照以下顺序处理异常：

1. `ZodValidationException`：返回 HTTP 400 和 `VALIDATION_FAILED`。
2. `ZodSerializationException`：记录完整日志，对客户端只返回通用 500，避免泄漏响应数据。
3. 普通 `HttpException`：兼容项目中现存的字符串异常和 `{ code, message }` 对象异常。
4. 未知异常：记录错误堆栈，统一返回安全的 500 响应。

不要把数据库、Redis 或第三方服务抛出的原始 `error.message` 直接返回给客户端。完整信息应写入服务端日志，客户端只接收安全文案。

## 6. 注册全局异常过滤器

修改：

```text
apps/server/src/app.module.ts
```

增加导入：

```ts
import { GlobalExceptionFilter } from '@/common/filters/global-exception.filter'
```

将 NestJS Core 的导入修改为：

```ts
import { APP_FILTER, APP_INTERCEPTOR, APP_PIPE } from '@nestjs/core'
```

在 `providers` 中增加：

```ts
{
  provide: APP_FILTER,
  useClass: GlobalExceptionFilter,
},
```

例如：

```ts
providers: [
  AppService,
  {
    provide: APP_FILTER,
    useClass: GlobalExceptionFilter,
  },
  {
    provide: APP_INTERCEPTOR,
    useClass: ResponseInterceptor,
  },
  {
    provide: APP_PIPE,
    useClass: ZodValidationPipe,
  },
  {
    provide: APP_INTERCEPTOR,
    useClass: ZodSerializerInterceptor,
  },
]
```

使用 `APP_FILTER` 注册后，过滤器由 NestJS 依赖注入系统创建，因此可以正常注入 `HttpAdapterHost`。

## 7. 替换 SessionAuthGuard 中的异常

修改：

```text
apps/server/src/modules/auth/guards/session-auth.guard.ts
```

增加导入：

```ts
import { AppException } from '@/common/exceptions/app.exception'
import { AUTH_ERRORS } from '../auth.errors'
```

从 `@nestjs/common` 的导入中移除 `UnauthorizedException`。

将缺少 Token 的异常：

```ts
if (!rawToken) {
  throw new UnauthorizedException({
    code: 'SESSION_TOKEN_MISSING',
    message: '缺少有效的登录 Token',
  })
}
```

改为：

```ts
if (!rawToken) {
  throw new AppException(AUTH_ERRORS.SESSION_TOKEN_MISSING)
}
```

将 Session 无效异常：

```ts
if (!auth) {
  throw new UnauthorizedException({
    code: 'SESSION_INVALID',
    message: '登录已失效，请重新登录',
  })
}
```

改为：

```ts
if (!auth) {
  throw new AppException(AUTH_ERRORS.SESSION_INVALID)
}
```

业务代码现在只负责表达“发生了哪一种错误”，不再负责拼装 HTTP 响应。

## 8. 逐步迁移其他异常

全局异常过滤器兼容现有 `HttpException`，因此不要求一次性替换全部异常。建议先注册过滤器，再按模块逐步迁移。

### 8.1 账号或密码错误

修改：

```text
apps/server/src/modules/auth/auth.service.ts
```

原来：

```ts
throw new UnauthorizedException('账号或密码错误')
```

改为：

```ts
throw new AppException(AUTH_ERRORS.INVALID_CREDENTIALS)
```

账号不存在、账号被禁用和密码错误继续使用同一个错误码，可以避免登录接口泄漏账号是否真实存在。

### 8.2 账号已存在

原来：

```ts
throw new ConflictException('账号已存在')
```

改为：

```ts
throw new AppException(AUTH_ERRORS.ACCOUNT_ALREADY_EXISTS)
```

HTTP 状态仍然是 `409 Conflict`。

### 8.3 当前 Session 用户失效

原来：

```ts
throw new UnauthorizedException({
  code: 'SESSION_USER_INVALID',
  message: '用户不存在或账号已不可用，请重新登录',
})
```

改为：

```ts
throw new AppException(AUTH_ERRORS.SESSION_USER_INVALID)
```

### 8.4 用户服务暂时不可用

原来：

```ts
throw new ServiceUnavailableException({
  code: 'USER_SERVICE_UNAVAILABLE',
  message: '暂时无法获取用户信息，请稍后重试',
})
```

改为：

```ts
throw new AppException(AUTH_ERRORS.USER_SERVICE_UNAVAILABLE)
```

HTTP 状态仍然是 `503 Service Unavailable`，不要把基础设施故障误报成用户未登录。

## 9. 调整统一响应类型

当前成功响应使用数字 `code`：

```json
{
  "code": 200,
  "data": {},
  "message": "success"
}
```

业务错误使用字符串 `code`：

```json
{
  "code": "SESSION_TOKEN_MISSING",
  "data": null,
  "message": "缺少有效的登录 Token"
}
```

因此响应类型需要允许 `number | string`。

### 9.1 修改服务端 ResOp

修改：

```text
apps/server/src/common/model/response.ts
```

将：

```ts
code: number
```

改为：

```ts
code: number | string
```

构造函数同步修改：

```ts
constructor(code: number | string, data: T, message = RESPONSE_SUCCESS_MSG) {
  this.code = code
  this.data = data
  this.message = message
}
```

错误方法改为：

```ts
static error(code: number | string, message?: string) {
  return new ResOp(code, null, message)
}
```

虽然异常过滤器会直接创建错误响应，但保持 `ResOp.error()` 的类型和统一协议一致，可以避免后续调用时再次出现 `{}` 与 `null` 不一致的问题。

### 9.2 修改共享响应类型

修改：

```text
packages/shared/src/types/common.ts
```

改为：

```ts
export interface ApiResponse<T> {
  code: number | string
  data: T | null
  message: string
}
```

当前 Web 请求层的业务码匹配类型已经允许 `number | string`，因此这一改动与现有请求层设计一致。

## 11. 推荐迁移顺序

为了避免一次修改过多文件，建议按照以下顺序进行：

1. 创建 `AppException`。
2. 创建 `AUTH_ERRORS`。
3. 创建并注册 `GlobalExceptionFilter`。
4. 调整服务端和共享响应类型。
5. 先替换 `SessionAuthGuard` 中的两个鉴权异常。
6. 手动验证 HTTP 401 和统一响应体。
7. 再替换 `AuthService`、`CurrentAuth` 和 `SessionStoreService` 中的其他异常。
8. 执行 `vp check` 和 Server 构建。
9. 后续补充异常过滤器和鉴权链路自动化测试。

过滤器兼容原有的 NestJS 异常格式，因此迁移期间允许下面两种代码暂时共存：

```ts
throw new UnauthorizedException('登录状态不存在')
```

```ts
throw new AppException(AUTH_ERRORS.SESSION_INVALID)
```

但最终业务模块内应优先使用集中定义的 `AppException`。

## 12. 与 nest-admin 方案的区别

`nest-admin` 采用的核心结构同样是：

```text
错误码字典
    +
BusinessException
    +
全局 ExceptionFilter
```

它的调用方式类似：

```ts
throw new BizException(ErrorEnum.INVALID_LOGIN)
```

这套分层方式值得借鉴，但当前项目不建议原样照搬以下设计：

### 12.1 不把所有业务错误都返回 HTTP 200

`nest-admin` 的业务异常通常使用 HTTP `200`，再通过响应体业务码判断成功或失败。

当前项目应保留真实 HTTP 语义：

```text
未认证       401
无权限       403
资源不存在   404
业务冲突     409
依赖不可用   503
未知错误     500
```

这样更适合网关、日志、监控、缓存以及当前 Web 请求层。

### 12.2 不使用 "code:message" 拼接字符串

`nest-admin` 的错误枚举使用类似下面的形式：

```ts
INVALID_LOGIN = '1101:登录无效，请重新登录'
```

然后在异常类中使用 `split(':')` 拆分。

当前项目使用结构化对象更安全：

```ts
{
  code: 'SESSION_TOKEN_MISSING',
  message: '缺少有效的登录 Token',
  status: HttpStatus.UNAUTHORIZED,
}
```

结构化对象具备完整类型检查，也不会因为文案中出现冒号而产生解析问题。

- [ ] Token 失效返回真正的 HTTP 401。

- [ ] 未知异常在服务端记录完整堆栈。
- [ ] 未知异常对客户端只返回通用 500 文案。
- [ ] `ApiResponse.code` 已允许 `number | string`。
