# NestJS 11 Server 统一异常处理改造指南

> 适用项目：当前 monorepo 中的 NestJS 11 + Fastify 5 + nestjs-zod + Zod 4 Server。
>
> 本文只讨论 Server 和服务端公共契约，不包含 React、Vue、Alova 或其他前端实现。
>
> 本文描述的是目标方案，会覆盖旧文档中“成功响应统一包装为 code/data/message”的约定。

## 1. 最终结论

当前项目统一采用下面的 HTTP 协议：

```text
Controller / Service / Guard
        │
        ├─ 成功
        │    └─ Controller 返回值作为响应正文直接返回
        │
        ├─ 可预期业务失败
        │    └─ AppException + 稳定业务错误码 + 正确 HTTP 状态
        │
        ├─ 请求参数校验失败
        │    └─ ZodValidationException
        │
        └─ 未知程序错误
             └─ Error
                    │
                    ▼
            GlobalExceptionFilter
            ├─ 统一失败正文
            ├─ 隐藏内部错误信息
            └─ 5xx 在 HTTP 边界记录一次

Fastify request.id
        ├─ 写入所有响应的 X-Request-Id
        └─ 写入错误边界日志
```

最终规则：

1. HTTP 2xx 的正文就是 Controller 返回的业务数据。
2. 成功响应不再增加 code、data、message 或 requestId。
3. HTTP 4xx/5xx 才返回统一失败正文。
4. 失败正文固定包含 code 和 message，可以包含结构化 details。
5. requestId 只通过 X-Request-Id 响应头对外提供，不放进 JSON 正文。
6. 所有响应都应携带 X-Request-Id，包括成功、失败、404、204 和 HEAD。
7. HTTP 状态表示错误类别，body.code 表示稳定的具体业务原因。
8. 不把业务失败伪装成 HTTP 200。
9. message 和 details 都必须是允许公开给调用方的安全信息。
10. stack、SQL、Redis 地址、Token、密码、请求头和第三方原始响应不得返回客户端。
11. 原始异常通过 cause 保留，5xx 只在最外层 HTTP Filter 记录一次。
12. 当前不接入 OpenTelemetry；X-Request-Id 使用服务端生成的 Fastify request.id。

## 2. 最终 HTTP 响应协议

### 2.1 成功响应

外壳。

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: 7cce0a42-2fe8-4c70-b9d1-6f11994863aa
```

```json
{
  "id": "user-id",
  "name": "Alice",
  "account": "alice"
}
```

数组也直接返回：

```http
HTTP/1.1 200 OK
X-Request-Id: a7eef69c-4055-4faa-8550-0f5cfa7801df
```

```json
[
  {
    "id": "user-1",
    "name": "Alice"
  },
  {
    "id": "user-2",
    "name": "Bob"
  }
]
```

创建资源时可以保留 NestJS 的 HTTP 201 语义：

```http
HTTP/1.1 201 Created
X-Request-Id: b8aa53de-f752-4981-babb-801795c4a6b8
```

```json
{
  "id": "new-user-id"
}
```

删除成功且不需要正文时返回 204：

```http
HTTP/1.1 204 No Content
X-Request-Id: 0837713f-a131-41a2-843e-52f82ad6d01d
```

204 和 HEAD 响应没有正文，但仍然必须携带 X-Request-Id。

分页结构属于业务 DTO，可以直接返回：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

这里的 items/page/pageSize/total 是接口自身的数据结构，不是全局响应包装。

### 2.2 普通业务失败

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/json
X-Request-Id: 7cce0a42-2fe8-4c70-b9d1-6f11994863aa
WWW-Authenticate: Bearer realm="api"
```

```json
{
  "code": "AUTH.SESSION_INVALID",
  "message": "登录已失效，请重新登录"
}
```

失败正文不再返回：

- data: null
- requestId
- statusCode
- error
- stack
- path
- timestamp

这些字段并非都绝对错误，但当前项目不需要在每个失败响应中重复它们。

HTTP 状态已经表达错误类别；请求关联信息统一放在 X-Request-Id 响应头。

### 2.3 参数校验失败

details 只在确实存在多条或字段级错误信息时返回，并保持结构化数组。

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Request-Id: 986fe43e-a6ce-4c84-a3fe-73f8c5601b71
```

```json
{
  "code": "COMMON.VALIDATION_FAILED",
  "message": "请求参数校验失败",
  "details": [
    {
      "path": "account",
      "code": "too_small",
      "message": "账号至少需要 4 个字符"
    },
    {
      "path": "password",
      "code": "too_small",
      "message": "密码至少需要 8 个字符"
    }
  ]
}
```

details 的规则：

- 普通业务错误通常不返回 details。
- details 固定为数组，不使用 string | array 之类的不稳定联合类型。
- path 是安全的字段路径，例如 account 或 profile.name。
- code 是字段级稳定代码，例如 too_small。
- message 是允许展示给用户的字段错误文案。
- 最多返回 20 条。
- 不返回用户原始输入值。
- 不返回整个 ZodError。
- 不把 Token、密码或其他秘密拼进 Zod 自定义 message。

### 2.4 未知服务端错误

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json
X-Request-Id: 267e37f0-a6ac-43e7-a45e-e27f590b74f2
```

```json
{
  "code": "COMMON.INTERNAL_SERVER_ERROR",
  "message": "服务器内部错误"
}
```

未知 500 的真实 message、stack 和 cause 只存在于服务端日志。

调用方需要反馈问题时，只需要提供 X-Request-Id，服务端即可查询对应错误日志。

### 2.5 HTTP 状态与业务错误码分工

| 场景                    | HTTP 状态 | body.code                     | 说明                       |
| ----------------------- | --------: | ----------------------------- | -------------------------- |
| 请求参数校验失败        |       400 | COMMON.VALIDATION_FAILED      | details 可以包含字段错误   |
| 缺少 Session Token      |       401 | AUTH.SESSION_TOKEN_MISSING    | 返回 Bearer challenge      |
| Session 无效或过期      |       401 | AUTH.SESSION_INVALID          | 返回 Bearer challenge      |
| 账号或密码错误          |       422 | AUTH.INVALID_CREDENTIALS      | 不冒充 Bearer Token 失效   |
| 无权限                  |       403 | AUTH.FORBIDDEN                | 已认证但没有访问权限       |
| 资源不存在              |       404 | 模块错误码或 COMMON.NOT_FOUND | 不暴露内部路径             |
| 账号已经存在            |       409 | AUTH.ACCOUNT_ALREADY_EXISTS   | 资源状态冲突               |
| 请求过于频繁            |       429 | COMMON.TOO_MANY_REQUESTS      | 知道窗口时设置 Retry-After |
| 数据库或 Redis 暂不可用 |       503 | 模块级稳定错误码              | 原始错误只进入日志         |
| 未知程序错误            |       500 | COMMON.INTERNAL_SERVER_ERROR  | 返回统一安全文案           |

body.code 必须是稳定字符串，不使用 HTTP 数字作为业务错误码。

建议格式：

```text
模块.具体原因

AUTH.SESSION_INVALID
AUTH.ACCOUNT_ALREADY_EXISTS
COMMON.VALIDATION_FAILED
```

错误码一旦成为公开契约，不应因为修改中文文案而改变。

## 4. 推荐改造顺序

不要先批量替换所有 throw。推荐按下面顺序执行：

1. 更新 shared 中的公开失败类型。
2. 删除成功响应包装。
3. 在 Fastify 根级 Hook 中设置 X-Request-Id。
4. 创建 AppException。
5. 创建公共和认证错误码目录。
6. 创建 GlobalExceptionFilter。
7. 迁移认证、Session、Redis 和数据库边界异常。
8. 注册 GlobalExceptionFilter。
9. 增加 Server 单元测试和 Fastify 集成测试。
10. 执行 shared 构建、vp check、Server 测试和 Server 构建。

把 Filter 注册放在用户可见异常迁移之后，可以避免迁移期间旧 HttpException 文案突然全部变成通用文案。

## 7. 配置服务端生成的 X-Request-Id

### 7.1 为什么继续使用 Fastify request.id

当前项目只是单个 NestJS HTTP Server，还没有 OpenTelemetry。

现阶段需要的是：

- 为每个 HTTP 请求生成不可预测的关联 ID。
- 响应头与错误日志使用同一个 ID。
- 调用方不能任意伪造 ID。
- 不增加新的运行时依赖。

Fastify request.id 已经满足这些要求。

### 7.2 调整 main.ts

修改：

```text
apps/server/src/main.ts
```

保留 Swagger 等现有逻辑，调整 FastifyAdapter 创建方式并增加根级 onRequest Hook：

```ts
import { randomUUID } from 'node:crypto'
import { AppModule } from '@/app.module'
import { logNetworkUrls } from '@/utils/server-address'
import { ConsoleLogger, Logger } from '@nestjs/common'
import { NestFactory } from '@nestjs/core'
import { FastifyAdapter, type NestFastifyApplication } from '@nestjs/platform-fastify'

async function bootstrap() {
  const adapter = new FastifyAdapter({
    trustProxy: ['127.0.0.1', '::1'],
    genReqId: () => randomUUID(),
  })

  adapter.getInstance().addHook('onRequest', (request, reply, done) => {
    reply.header('x-request-id', request.id)
    done()
  })

  const app = await NestFactory.create<NestFastifyApplication>(AppModule, adapter, {
    logger: new ConsoleLogger({
      json: process.env.NODE_ENV === 'production',
      colors: process.env.NODE_ENV === 'development',
    }),
  })

  app.enableCors({
    origin: ['*'],
    allowedHeaders: ['Content-Type', 'Authorization', 'X-Company-Id'],
    methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
    exposedHeaders: ['X-Request-Id', 'WWW-Authenticate', 'Retry-After'],
  })

  // 保留当前 Swagger 配置

  const port = Number.parseInt(process.env.PORT ?? '3000', 10)
  const host = process.env.HOST ?? '0.0.0.0'

  await app.listen(port, host)
  logNetworkUrls(port)
}

void bootstrap().catch((cause: unknown) => {
  const logger = new Logger('Bootstrap')
  logger.error('Server bootstrap failed', cause instanceof Error ? cause.stack : undefined)
  process.exitCode = 1
})
```

根级 Fastify Hook 比成功拦截器更适合设置 X-Request-Id：

- 不修改 Controller 返回值。
- 能覆盖正常路由。
- 能覆盖 404。
- 能覆盖 CORS 预检。
- 能覆盖 204 和 HEAD。
- 失败 Filter 不需要生成第二个 ID。

GlobalExceptionFilter 仍会防御性地再次设置同一个响应头，避免未来 Hook 被误删或 Filter 被单独测试时丢失 Header。

### 7.3 不要信任调用方传入的请求 ID

不要配置：

```ts
requestIdHeader: 'x-request-id'
```

启用该配置后，Fastify 会直接使用调用方传入的值，默认不会替项目校验长度和字符集。

这可能造成：

- 日志伪造。
- 超长日志字段。
- 同一个 ID 被恶意复用。
- 多个请求在日志系统中被错误关联。

当前继续使用：

```ts
genReqId: () => randomUUID()
```

如果未来由可信 API Gateway 统一生成 X-Request-Id，应在 genReqId 中同时验证：

- 请求确实来自可信代理。
- 只允许有限字符集。
- 最大长度不超过 80。
- 非法或缺失时重新生成。

### 7.4 X-Request-Id 的统一规则

1. Header 名在代码中统一写 x-request-id。
2. 文档和示例中显示为 X-Request-Id。
3. HTTP Header 名大小写不敏感。
4. JSON 正文不再出现 requestId。
5. Filter 日志字段统一命名 requestId。
6. 不把 requestId 当作用户身份或安全凭据。
7. 代理、网关和日志采集系统必须保留该 Header。

## 8. 创建类型安全的 AppException

新建：

```text
apps/server/src/common/exceptions/app.exception.ts
```

```ts
import { HttpException, type HttpStatus } from '@nestjs/common'
import type { ApiErrorDetail } from 'shared/types'

const ERROR_CODE_PATTERN = /^[A-Z][A-Z0-9_]*(?:\.[A-Z][A-Z0-9_]*)+$/

export interface AppErrorDefinition<Code extends string = string> {
  readonly code: Code
  readonly publicMessage: string
  readonly status: HttpStatus
  readonly bearerChallenge?: true
}

export interface AppExceptionOptions {
  readonly cause?: unknown
  readonly details?: readonly ApiErrorDetail[]
}

function assertErrorDefinition(definition: AppErrorDefinition): void {
  if (!ERROR_CODE_PATTERN.test(definition.code) || definition.code.length > 80) {
    throw new TypeError('Invalid application error code: ' + definition.code)
  }

  if (definition.status < 400 || definition.status > 599) {
    throw new TypeError('Application error status must be between 400 and 599')
  }

  if (!definition.publicMessage.trim()) {
    throw new TypeError('Application error publicMessage must not be empty')
  }

  if (definition.bearerChallenge && definition.status !== 401) {
    throw new TypeError('bearerChallenge is only valid for HTTP 401')
  }

  if (definition.status === 401 && !definition.bearerChallenge) {
    throw new TypeError('HTTP 401 errors must declare bearerChallenge')
  }
}

export class AppException extends HttpException {
  readonly definition: AppErrorDefinition
  readonly details?: readonly ApiErrorDetail[]

  constructor(definition: AppErrorDefinition, options: AppExceptionOptions = {}) {
    assertErrorDefinition(definition)

    super(definition.publicMessage, definition.status, {
      cause: options.cause,
    })

    this.name = AppException.name
    this.definition = definition
    this.details = options.details
  }
}
```

AppException 的职责：

- 绑定稳定错误码、公开文案和 HTTP 状态。
- 可选携带公开的结构化 details。
- 使用 cause 保存原始异常。
- 不在 Service 中拼装最终 HTTP JSON。
- 不在 Service 中重复记录基础设施异常。

业务代码只抛异常：

```ts
throw new AppException(AUTH_ERRORS.SESSION_INVALID)
```

带原始异常：

```ts
throw new AppException(AUTH_ERRORS.SERVICE_UNAVAILABLE, {
  cause,
})
```

```ts
import { AppException } from '@/common/exceptions/app.exception'
import { COMMON_ERRORS } from '@/common/errors/common.errors'
import {
  ArgumentsHost,
  Catch,
  type ExceptionFilter,
  HttpException,
  HttpStatus,
  Logger,
} from '@nestjs/common'
import { HttpAdapterHost } from '@nestjs/core'
import type { FastifyReply, FastifyRequest } from 'fastify'
import { ZodSerializationException, ZodValidationException } from 'nestjs-zod'
import type { ApiErrorDetail, ApiFailure } from 'shared/types'
import { ZodError } from 'zod'

const MAX_DETAIL_COUNT = 20
const MAX_DETAIL_PATH_LENGTH = 200
const MAX_DETAIL_CODE_LENGTH = 80
const MAX_PUBLIC_MESSAGE_LENGTH = 300
const MAX_LOG_MESSAGE_LENGTH = 1000
const MAX_LOG_FRAME_LENGTH = 600
const MAX_LOG_STACK_FRAMES = 12

interface NormalizedFailure {
  readonly status: number
  readonly body: ApiFailure
  readonly cause?: unknown
  readonly bearerChallenge?: boolean
}

interface PublicHttpError {
  readonly code: string
  readonly message: string
}

const PUBLIC_HTTP_ERRORS: Readonly<Record<number, PublicHttpError>> = {
  [HttpStatus.BAD_REQUEST]: {
    code: 'COMMON.BAD_REQUEST',
    message: '请求内容无效',
  },
  [HttpStatus.UNAUTHORIZED]: {
    code: 'COMMON.UNAUTHORIZED',
    message: '身份认证失败',
  },
  [HttpStatus.FORBIDDEN]: {

    message: '没有权限执行此操作',
  },
  [HttpStatus.NOT_FOUND]: {
    code: 'COMMON.NOT_FOUND',
    message: '请求的资源不存在',
  },
  [HttpStatus.METHOD_NOT_ALLOWED]: {
    code: 'COMMON.METHOD_NOT_ALLOWED',
    message: '请求方法不受支持',
  },
  [HttpStatus.CONFLICT]: {
    code: 'COMMON.CONFLICT',
    message: '当前资源状态存在冲突',
  },
  [HttpStatus.PAYLOAD_TOO_LARGE]: {
    code: 'COMMON.PAYLOAD_TOO_LARGE',
    message: '请求内容过大',
  },
  [HttpStatus.UNSUPPORTED_MEDIA_TYPE]: {
    code: 'COMMON.UNSUPPORTED_MEDIA_TYPE',
    message: '请求内容类型不受支持',
  },
  [HttpStatus.UNPROCESSABLE_ENTITY]: {
    code: 'COMMON.UNPROCESSABLE_CONTENT',

  },
  [HttpStatus.TOO_MANY_REQUESTS]: {
    code: 'COMMON.TOO_MANY_REQUESTS',
    message: '请求过于频繁，请稍后重试',

function cleanPublicText(value: unknown, maxLength: number): string {
  if (typeof value !== 'string') {
    return ''
  }

  return value
    .replace(/[\u0000-\u001F\u007F-\u009F\u2028\u2029]/g, ' ')
    .trim()
    .slice(0, maxLength)
}

function cleanDetailCode(value: unknown): string {
  const code = cleanPublicText(value, MAX_DETAIL_CODE_LENGTH)

  if (/^[A-Za-z][A-Za-z0-9._-]*$/.test(code)) {
    return code
  }

  return 'invalid'
}

function normalizeDetails(
  details: readonly ApiErrorDetail[] | undefined,
): ApiErrorDetail[] | undefined {
  const normalized = details?.slice(0, MAX_DETAIL_COUNT).map((detail) => {
    const path = cleanPublicText(detail.path, MAX_DETAIL_PATH_LENGTH)
    const message = cleanPublicText(detail.message, MAX_PUBLIC_MESSAGE_LENGTH) || '请求内容无效'

    return {
      ...(path ? { path } : {}),
      code: cleanDetailCode(detail.code),
      message,
    }
  })

  return normalized?.length ? normalized : undefined
}

function normalizeStatus(value: unknown): number {
  if (typeof value !== 'number' || !Number.isInteger(value)) {
    return HttpStatus.INTERNAL_SERVER_ERROR
  }

  if (value < 400 || value > 599) {
    return HttpStatus.INTERNAL_SERVER_ERROR
  }

  return value
}

function sanitizeLogText(value: string, maxLength: number): string {
  return value
    .replace(/[\u0000-\u001F\u007F\u2028\u2029]/g, ' ')
    .replace(/\b([a-z][a-z0-9+.-]*:\/\/)([^@\s/]+)@/gi, '$1[REDACTED]@')
    .replace(/\b(Bearer|Basic)\s+[A-Za-z0-9._~+\/=-]+/gi, '$1 [REDACTED]')
    .replace(
      /([?&](?:password|passwd|pwd|token|access[_-]?token|refresh[_-]?token|api[_-]?key|secret|client[_-]?secret)=)[^&#\s]*/gi,
      '$1[REDACTED]',
    )
    .replace(
      /(["']?)(authorization|proxy-authorization|cookie|set-cookie)\1\s*[:=]\s*(?:"[^"]*"|'[^']*'|[^,}\]]+)/gi,
      '$1$2$1=[REDACTED]',
    )
    .replace(
      /(["']?)(password|passwd|pwd|token|access[_-]?token|refresh[_-]?token|api[_-]?key|x-api-key|secret|client[_-]?secret|database[_-]?url|redis[_-]?url|connection[_-]?string|dsn)\1\s*[:=]\s*(?:"[^"]*"|'[^']*'|[^\s,;}\]]+)/gi,
      '$1$2$1=[REDACTED]',
    )
    .replace(/\s+/g, ' ')
    .trim()
    .slice(0, maxLength)
}

function sanitizeStackFrames(error: Error): string[] | undefined {
  if (!error.stack || /[\r\n\u2028\u2029]/.test(error.message)) {
    return undefined
  }

  const frames = error.stack
    .split(/\r?\n/)
    .slice(1)
    .map((line) => line.trim())
    .filter((line) => line.startsWith('at '))
    .slice(0, MAX_LOG_STACK_FRAMES)
    .map((line) => sanitizeLogText(line, MAX_LOG_FRAME_LENGTH))
    .filter(Boolean)

  return frames.length ? frames : undefined
}

function serializeError(value: unknown, depth = 0): Record<string, unknown> {
  if (!(value instanceof Error)) {
    return {
      type: typeof value,
    }
  }

  const stackFrames = sanitizeStackFrames(value)
  const result: Record<string, unknown> = {
    name: sanitizeLogText(value.name, 120) || 'Error',
    message: sanitizeLogText(value.message, MAX_LOG_MESSAGE_LENGTH),
    ...(stackFrames ? { stackFrames } : {}),
  }

  if (depth < 2 && value.cause !== undefined) {
    result.cause = serializeError(value.cause, depth + 1)
  }

  return result
}

@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name)

  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost): void {
    const http = host.switchToHttp()
    const request = http.getRequest<FastifyRequest>()
    const response = http.getResponse<FastifyReply>()
    const requestId = String(request.id)
    const normalized = this.normalize(exception)
    const { httpAdapter } = this.adapterHost

    if (normalized.status >= 500) {
      this.logServerFailure(exception, normalized, request, requestId)
    }

    if (httpAdapter.isHeadersSent(response)) {
      httpAdapter.end(response)
      return
    }

    httpAdapter.setHeader(response, 'x-request-id', requestId)

    if (normalized.bearerChallenge) {
      httpAdapter.setHeader(response, 'www-authenticate', 'Bearer realm="api"')
    }

    httpAdapter.reply(response, normalized.body, normalized.status)
  }

  private normalize(exception: unknown): NormalizedFailure {
    if (exception instanceof ZodSerializationException) {
      return {
        status: HttpStatus.INTERNAL_SERVER_ERROR,
        body: {
          code: COMMON_ERRORS.INTERNAL_SERVER_ERROR.code,
          message: COMMON_ERRORS.INTERNAL_SERVER_ERROR.publicMessage,
        },
        cause: exception.getZodError() ?? exception,
      }
    }

    if (exception instanceof ZodValidationException) {
      const details = this.getZodDetails(exception)

      return {
        status: COMMON_ERRORS.VALIDATION_FAILED.status,
        body: {
          code: COMMON_ERRORS.VALIDATION_FAILED.code,
          message: COMMON_ERRORS.VALIDATION_FAILED.publicMessage,
          ...(details?.length ? { details } : {}),
        },
      }
    }

    if (exception instanceof AppException) {
      const status = normalizeStatus(exception.getStatus())
      const details = normalizeDetails(exception.details)
      const message =
        cleanPublicText(exception.definition.publicMessage, MAX_PUBLIC_MESSAGE_LENGTH) ||
        '请求处理失败'

      return {
        status,
        body: {
          code: exception.definition.code,
          message,
          ...(details?.length ? { details } : {}),
        },
        cause: status >= 500 ? (exception.cause ?? exception) : undefined,
        bearerChallenge: exception.definition.bearerChallenge,
      }
    }

    if (exception instanceof HttpException) {
      return this.normalizeLegacyHttpException(exception)
    }

    return {
      status: HttpStatus.INTERNAL_SERVER_ERROR,
      body: {
        code: COMMON_ERRORS.INTERNAL_SERVER_ERROR.code,
        message: COMMON_ERRORS.INTERNAL_SERVER_ERROR.publicMessage,
      },
      cause: exception,
    }
  }

  private getZodDetails(exception: ZodValidationException): ApiErrorDetail[] | undefined {
    const zodError = exception.getZodError()

    if (!(zodError instanceof ZodError)) {
      return undefined
    }

    const details = zodError.issues.slice(0, MAX_DETAIL_COUNT).map((issue) => {
      const path = cleanPublicText(issue.path.map(String).join('.'), MAX_DETAIL_PATH_LENGTH)
      const message = cleanPublicText(issue.message, MAX_PUBLIC_MESSAGE_LENGTH) || '请求内容无效'

      return {
        ...(path ? { path } : {}),
        code: cleanDetailCode(issue.code),
        message,
      }
    })

    return details.length ? details : undefined
  }

  private normalizeLegacyHttpException(exception: HttpException): NormalizedFailure {
    const status = normalizeStatus(exception.getStatus())

    if (status >= 500) {
      const serviceUnavailable =
        status === HttpStatus.BAD_GATEWAY ||
        status === HttpStatus.SERVICE_UNAVAILABLE ||
        status === HttpStatus.GATEWAY_TIMEOUT

      return {
        status,
        body: serviceUnavailable
          ? {
              code: COMMON_ERRORS.SERVICE_UNAVAILABLE.code,
              message: COMMON_ERRORS.SERVICE_UNAVAILABLE.publicMessage,
            }
          : {
              code: COMMON_ERRORS.INTERNAL_SERVER_ERROR.code,
              message: COMMON_ERRORS.INTERNAL_SERVER_ERROR.publicMessage,
            },
        cause: exception,
      }
    }

    const publicError = PUBLIC_HTTP_ERRORS[status] ?? {
      code: 'COMMON.HTTP_' + status,
      message: '请求处理失败',
    }

    return {
      status,
      body: publicError,
      bearerChallenge: status === HttpStatus.UNAUTHORIZED,
    }
  }

  private logServerFailure(
    exception: unknown,
    normalized: NormalizedFailure,
    request: FastifyRequest,
    requestId: string,
  ): void {
    const route = request.routeOptions?.url ?? 'unmatched'
    const cause = normalized.cause ?? exception

    this.logger.error({
      event: 'http_request_failed',
      requestId,
      method: request.method,
      route,
      status: normalized.status,
      code: normalized.body.code,
      error: serializeError(cause),
    })
  }
}
```

### 10.1 Filter 的安全边界

GlobalExceptionFilter 不读取并透传任意异常对象上的 message。

原因：

- PostgreSQL 错误可能包含表、列或约束信息。
- Redis 错误可能包含地址或命令信息。
- 第三方 SDK 错误可能包含 URL、Token 或原始响应。
- 未知 Error 的 message 是开发信息，不是公开协议。
- NestJS 的默认 HttpException 对象格式不保证符合当前项目协议。

只有两类文案可以返回：

1. 错误目录中的固定 publicMessage。
2. 经过约束的 Zod 字段校验 message。

### 10.2 为什么旧 HttpException 不再透传 message

迁移期间如果仍然存在：

```ts
throw new UnauthorizedException('某个动态消息')
```

Filter 会保留 HTTP 状态，但返回通用安全正文，不继续信任这个动态 message。

因此应优先迁移用户可见的认证和业务异常，然后再注册 Filter。

### 10.3 Filter 不记录什么

异常 Filter 默认不记录：

- 完整请求 URL。
- query。
- body。
- headers。
- Authorization。
- Cookie。
- Session Token。
- 密码。
- 用户提交的任意文本。

日志只记录：

- requestId。
- method。
- 路由模板。
- HTTP status。
- 业务 code。
- 受限的错误和 cause 链。

必须审计的业务字段应进入独立的白名单审计日志，不应通过异常 Filter 顺手记录整个请求。

### 12.2 AuthService

```text

```

账号已存在：


在 AuthService 文件顶部保存一个固定的 dummy hash。它不是任何用户的凭据，
只用于让所有登录失败路径都执行一次相同参数的 Argon2 verify：

```ts
const LOGIN_DUMMY_PASSWORD_HASH =
  '$argon2id$v=19$m=65536,p=4,t=3$/sDN9pcO6kkAcm+ncFtbdA$vmQIsQtUG9E+s22x70njKji67RJDseq12y/sYFG7iNk'
```

登录校验改为：

```ts
const user = await this.authRepository.findByAccount(account)
const passwordHash = user?.status === 'active' ? user.passwordHash : LOGIN_DUMMY_PASSWORD_HASH
const passwordMatches = await this.passwordService.verify(passwordHash, input.password)

if (!user || user.status !== 'active' || !passwordMatches) {
  throw new AppException(AUTH_ERRORS.INVALID_CREDENTIALS)
}
```

这样账号不存在、账号禁用、密码错误和登录成功都会执行一次 verify。
dummy hash 必须由当前 PasswordService.hash 的同一套 Argon2 参数生成；以后调整
Argon2 参数时也要重新生成它。错误正文始终使用同一个
AUTH.INVALID_CREDENTIALS，不通过 message 或 details 暴露账号是否存在。

```ts

  throw new AppException(AUTH_ERRORS.SERVICE_UNAVAILABLE, {
    cause,
  })
```

## 13. 迁移 Redis 和数据库错误

### 13.1 Redis Session 边界

当前 SessionStoreService.execute 会先记录 Redis 错误，再抛出新的 ServiceUnavailableException。

如果 GlobalExceptionFilter 又记录一次，就会形成重复日志。

目标实现：

```ts
private async execute(command: () => Promise<unknown>) {
  try {
    const result = await command()

    if (!Array.isArray(result)) {
      throw new Error('Redis script returned a non-array result')
    }

    return result.map((item) => String(item ?? ''))
  } catch (cause) {
    throw new AppException(AUTH_ERRORS.SERVICE_UNAVAILABLE, {
      cause,
    })
  }
}
```

调整原则：

- Session 过期、被替换、已退出属于正常业务结果，可以返回 null。
- Redis 连接失败、脚本结果异常属于 503。
- 底层 Service 不重复 logger.error。
- 原始错误通过 cause 交给最外层 Filter。
- 客户端只看到 AUTH.SERVICE_UNAVAILABLE。

### 13.2 数据库边界

数据库错误应在 Repository 或 Service 边界映射：

```ts
try {
  return await this.authRepository.createUser(input)
} catch (cause) {
  if (isKnownAccountConflict(cause)) {
    throw new AppException(AUTH_ERRORS.ACCOUNT_ALREADY_EXISTS, {
      cause,
    })
  }

  throw new AppException(AUTH_ERRORS.SERVICE_UNAVAILABLE, {
    cause,
  })
}
```

不要：

- 把数据库错误 message 返回客户端。
- 依赖字符串 contains 判断所有数据库错误。
- 在 Repository、Service 和 Filter 三层重复记录同一个异常。
- 把唯一约束名、SQL 或连接地址放进 details。

已知约束冲突应使用数据库驱动提供的稳定错误码或明确的约束映射。

### 13.3 第三方服务

第三方 SDK 或 HTTP 调用错误应在对应 Adapter 边界映射：

```ts
try {
  return await this.thirdPartyClient.call(input)
} catch (cause) {
  throw new AppException(MODULE_ERRORS.UPSTREAM_UNAVAILABLE, {
    cause,
  })
}
```

不要把第三方完整响应透传给客户端。

## 14. 401、WWW-Authenticate 与登录失败

受 Bearer Token 保护的资源返回 401 时，应携带：

```http
WWW-Authenticate: Bearer realm="api"
```

适用：

- 缺少 Session Token。
- Token 无效。
- Session 已过期。
- 用户已被禁用，当前 Session 不能继续使用。

JSON 账号密码登录失败使用 422：

```json
{
  "code": "AUTH.INVALID_CREDENTIALS",
  "message": "账号或密码错误"
}
```

它不是一个正在等待 Bearer Token 的受保护资源，因此不设置 Bearer challenge。

如果未来实现标准 OAuth 2.0 Token Endpoint，应按 OAuth 规范重新定义该接口，不直接沿用当前约定。

## 15. Retry-After

429 或部分 503 可以携带：

```http
Retry-After: 30
```

但只有真正知道重试窗口的组件才能设置：

- 限流器设置 429 的 Retry-After。
- 上游适配层在明确知道恢复时间时设置 503 的 Retry-After。

通用 GlobalExceptionFilter 不应猜测重试时间。

```ts
  code!: string

  @ApiProperty({ example: '请求参数校验失败' })
  message!: string

  @ApiPropertyOptional({
    type: () => [ApiErrorDetailDto],
  })
  details?: ApiErrorDetailDto[]
}
```

Controller 文档示例：

```ts
@ApiOkResponse({ type: AuthUserDto })
@ApiBadRequestResponse({ type: ApiFailureDto })
@ApiUnauthorizedResponse({ type: ApiFailureDto })
@Get('me')
getCurrentUser() {
  // ...
}
```

X-Request-Id 是响应 Header，不要使用 ApiHeader；ApiHeader 描述的是调用方发送的
请求 Header。应把 headers 写在实际的响应装饰器中：

```ts
@ApiOkResponse({
  type: AuthUserDto,
  headers: {
    'X-Request-Id': {
      description: '服务端生成的请求关联 ID',
      schema: {
        type: 'string',
        format: 'uuid',
      },
    },
  },
})
```

失败响应装饰器也应声明同一个 Header。项目接口较多时，封装公共响应装饰器统一
加入 headers，避免每个 Controller 复制；但不要把 X-Request-Id 声明成请求参数。

## 17. 启动和非 HTTP 错误边界

GlobalExceptionFilter 只处理进入 NestJS HTTP 生命周期的异常。

它不负责：

- bootstrap 失败。
- 后台任务异常。
- 消息队列消费者异常。
- 定时任务异常。
- WebSocket/RPC 异常。
- uncaughtException。
- unhandledRejection。

bootstrap 使用明确的 Promise catch：

```ts
void bootstrap().catch((cause: unknown) => {
  const logger = new Logger('Bootstrap')
  logger.error('Server bootstrap failed', cause instanceof Error ? cause.stack : undefined)
  process.exitCode = 1
})
```

不要在 GlobalExceptionFilter 构造器中注册 process.on。

不同传输层应有独立错误边界，不能假设 HTTP Filter 会自动捕获所有异步任务错误。

## 20. 日志策略

### 20.1 4xx

正常、可预期的业务 4xx 默认不记录 error：

- 账号或密码错误。
- Session 过期。
- 参数校验失败。
- 资源冲突。
- 无权限。

确实需要安全审计的事件应走独立审计日志，而不是全部作为程序异常。

### 20.2 5xx

5xx 在 GlobalExceptionFilter 统一记录一次：

```json
{
  "event": "http_request_failed",
  "requestId": "267e37f0-a6ac-43e7-a45e-e27f590b74f2",
  "method": "GET",
  "route": "/auth/me",
  "status": 503,
  "code": "AUTH.SERVICE_UNAVAILABLE",
  "error": {
    "name": "Error"
  }
}
```

响应：

```http
X-Request-Id: 267e37f0-a6ac-43e7-a45e-e27f590b74f2
```

调用方提供该 ID 后，可以直接定位日志。

### 20.3 不重复日志

不推荐：

```text
Repository logger.error
  └─ Service logger.error
       └─ Filter logger.error
```

推荐：

```text
Repository / Service
  └─ AppException({ cause })
       └─ GlobalExceptionFilter 记录一次
```

如果某一层已经完成重试并成功恢复，不需要向 Filter 抛异常。

## 21. 本次不接入 OpenTelemetry

当前 X-Request-Id 只解决：

- HTTP 响应与服务端错误日志关联。
- 单次请求定位。
- 并发请求区分。

它不提供：

- 跨服务 Trace。
- Span 父子关系。
- 数据库和 Redis 调用耗时瀑布图。
- traceparent 传播。
- 采样和 Trace 导出。

这些能力等项目出现多服务调用、异步任务或性能排查需求时再接入。

未来接入 OpenTelemetry 时，可以同时保留：

- X-Request-Id：单次 HTTP 请求 ID。
- traceparent：W3C 链路上下文。
- traceId/spanId：写入日志和 Trace 后端。

不要在当前阶段把 UUID request.id 改名成 OpenTelemetry traceId。
