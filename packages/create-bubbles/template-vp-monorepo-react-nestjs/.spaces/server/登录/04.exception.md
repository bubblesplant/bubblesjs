# NestJS 11 全链路统一错误处理改造指南

> 适用项目：当前 monorepo 的 NestJS 11 + Fastify 5 + `nestjs-zod` + React/Vue + Alova Axios Adapter。
>
> 调研快照：2026-08-18。本文对照了 `buqiyuan/nest-admin`、`linlingqin77/Nest-Admin-Soybean`、NestJS/Fastify 官方文档、RFC 9457、OWASP 和 Axios 文档。

## 1. 先给结论

当前项目最适合的方案是：

```text
Controller / Service / Guard
        │
        ├─ 可预期业务失败 ──> AppException + 稳定错误码 + 正确 HTTP 状态
        │
        ├─ Zod 请求失败 ───> ZodValidationException
        │
        └─ 未知程序错误 ───> Error
                                │
                                ▼
                    GlobalExceptionFilter
                    ├─ 安全响应给客户端
                    ├─ 5xx 在 HTTP 边界统一记录一次
                    └─ 错误响应和边界日志使用同一个 requestId

正常返回 ────────────────> ResponseInterceptor

Axios 2xx ───────────────> responded.onSuccess
Axios 4xx / 5xx ─────────> responded.onError 解析 error.response.data
```

最终规则：

1. 成功响应继续由现有 `ResponseInterceptor` 包装。
2. 失败响应只由全局 `GlobalExceptionFilter` 包装。
3. 不把业务失败伪装成 HTTP `200`。
4. HTTP 状态表达错误类别，响应体 `code` 表达具体业务原因。
5. 业务错误码使用带模块前缀的稳定字符串，例如 `AUTH.SESSION_INVALID`。
6. 客户端永远看不到堆栈、SQL、Redis 地址、Token、密码或第三方原始响应。
7. 原始异常通过 `cause` 保留，5xx 只在最外层 HTTP Filter 记录一次。
8. HTTP 响应携带 `requestId`；错误边界日志使用同一个 ID，便于从前端报错定位服务端日志。
9. 前端不能只按 HTTP `401` 跳登录页，必须区分“Session 失效”和“账号密码错误”。

## 2. 为什么不直接复制两个参考项目

### 2.1 方案对比

| 方案                     | 值得借鉴                                                                                   | 不应照搬                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `buqiyuan/nest-admin`    | `APP_FILTER`、成功拦截器与异常过滤器分工、生产隐藏未知 500                                 | 业务错误经常返回 HTTP 200；`"1001:消息"` 再 `split(':')`；Filter 构造器注册进程监听器；无 requestId；丢失部分结构化异常信息                              |
| `Nest-Admin-Soybean`     | requestId、错误码文档、独立认证/授权异常、结构化日志、响应拦截器                           | 业务错误仍返回 200；Express 专用；直接信任客户端 `X-Request-Id`；开发环境向客户端返回 stack；未知 5xx 仍可能返回原始消息；请求体仅浅层脱敏且可能重复日志 |
| NestJS 官方              | `APP_FILTER`、`HttpAdapterHost`、标准 HTTP 状态、异常 `cause`、独立传输层 Filter           | 官方只提供基础骨架，业务错误码、脱敏和前端协议需要项目自行设计                                                                                           |
| RFC 9457 Problem Details | 公共 API 的标准错误格式和 `application/problem+json`                                       | 当前两个前端已经依赖 `{ code, data, message }`，立即切换会扩大改造面                                                                                     |
| 本文方案                 | 保留现有响应协议，补齐 HTTP 语义、稳定错误码、requestId、cause、脱敏、Axios 错误分支和测试 | 暂不强制引入 Pino、OpenTelemetry 或 RFC 9457，先完成低风险基础改造                                                                                       |

### 2.2 对 `nest-admin` 的判断

调研时默认分支 HEAD 为 [`2eeccc4`](https://github.com/buqiyuan/nest-admin/commit/2eeccc4cb699d1aedbe04b4437a9d095cde02c74)，提交时间为 2025-06-10；其异常核心实现主要形成于 2024 年。

值得保留的骨架：

```text
错误码目录 + 自定义业务异常 + 全局 Filter + 成功 Interceptor
```

必须改写的部分：

- `BusinessException` 不应固定使用 HTTP 200。
- 不使用 `code:message` 拼接字符串。
- 不在 HTTP Filter 构造器里注册 `uncaughtException` 和 `unhandledRejection`。
- 不读取任意异常对象上的 `status/statusCode` 后直接信任。
- 不把数据库或 Redis 原始异常消息返回客户端。

### 2.3 对 `Nest-Admin-Soybean` 的判断

调研时默认分支 HEAD 为 [`83a83f7`](https://github.com/linlingqin77/Nest-Admin-Soybean/commit/83a83f72189565e4eff3f2ca074f558d82e907e5)，异常相关核心文件在 2026-03-22 的 [`866475d`](https://github.com/linlingqin77/Nest-Admin-Soybean/commit/866475d374c31b4b317f41089da40abd2e13dbfd) 中重构。它已经加入 requestId、错误码文档、全局 Filter 和结构化日志，方向更完整。

但当前项目是 Fastify，不能复制它的 Express 代码：

```ts
const response = ctx.getResponse<Response>()
response.status(httpStatus).json(payload)
```

本文改用 NestJS 官方推荐的 `HttpAdapterHost`：

```ts
httpAdapter.reply(response, payload, status)
```

同时不接受它的以下做法：

- 业务异常使用 HTTP 200。
- 无校验地接受调用方提供的 `X-Request-Id`。
- 在开发环境把 stack 放进响应体。
- 记录整个请求 body 后再做浅层字段替换。
- 未知 `HttpException` 为 5xx 时仍暴露其 message。

## 3. 当前项目的问题清单

当前版本和结构：

- NestJS：锁文件实际为 11.1.28。
- Fastify：项目直接依赖 5.8.5，Nest Fastify Adapter 内部依赖 5.10.0。
- `nestjs-zod`：5.5.0。
- Zod：4.4.3。
- 成功响应：`apps/server/src/common/interceptors/transform.ts`。
- 全局 Pipe：`ZodValidationPipe`。
- 响应序列化：`ZodSerializerInterceptor`。
- 当前没有 `APP_FILTER`。

现在会出现多种错误格式：

```json
{
  "statusCode": 401,
  "message": "账号或密码错误",
  "error": "Unauthorized"
}
```

```json
{
  "code": "SESSION_INVALID",
  "message": "登录已失效，请重新登录"
}
```

```json
{
  "statusCode": 400,
  "message": "Validation failed",
  "errors": []
}
```

此外还有几个容易漏掉的前端问题：

- React 和 Vue 都使用 Axios Adapter；Axios 默认把 4xx/5xx 送进 `responded.onError`。
- 当前 `onError` 只读取 `error.message`，没有读取 `error.response.data`。
- 当前 `onError` 不执行 Session 失效跳转。
- 两个前端把 `responseMessageKey` 配成了 `msg`，服务端实际字段是 `message`。
- Vue 只把 HTTP 200 当成功，但 NestJS 的 POST 默认可能返回 201。
- 如果全局按所有 HTTP 401 跳登录，登录接口的“账号或密码错误”也会被误判为 Session 过期。

因此，这次必须同时改服务端和两个前端的错误分支。

## 4. 目标响应协议

### 4.1 成功响应

```http
HTTP/1.1 200 OK
X-Request-Id: 0dfad9bd-0de2-4552-bfd5-8a29ef94be23
```

```json
{
  "code": 200,
  "data": {
    "id": "user-id"
  },
  "message": "success",
  "requestId": "0dfad9bd-0de2-4552-bfd5-8a29ef94be23"
}
```

### 4.2 业务失败

```http
HTTP/1.1 401 Unauthorized
X-Request-Id: 0dfad9bd-0de2-4552-bfd5-8a29ef94be23
WWW-Authenticate: Bearer realm="api"
```

```json
{
  "code": "AUTH.SESSION_INVALID",
  "data": null,
  "message": "登录已失效，请重新登录",
  "requestId": "0dfad9bd-0de2-4552-bfd5-8a29ef94be23"
}
```

### 4.3 参数校验失败

```http
HTTP/1.1 400 Bad Request
```

```json
{
  "code": "COMMON.VALIDATION_FAILED",
  "data": null,
  "message": "请求参数校验失败",
  "requestId": "0dfad9bd-0de2-4552-bfd5-8a29ef94be23",
  "details": [
    {
      "path": "account",
      "code": "too_small",
      "message": "Too small: expected string to have >=4 characters"
    }
  ]
}
```

只返回 Zod issue 的 `path`、`code`、`message`，不要返回整个 ZodError，也不要返回原始输入值。Zod 的自定义 message 本身属于公开协议，编写 `refine()` 等校验时禁止把用户原始值拼进 message；Filter 只能做长度和控制字符清洗，无法判断一段业务文本里是否包含秘密。

### 4.4 未知服务端错误

```http
HTTP/1.1 500 Internal Server Error
```

```json
{
  "code": "COMMON.INTERNAL_SERVER_ERROR",
  "data": null,
  "message": "服务器内部错误",
  "requestId": "0dfad9bd-0de2-4552-bfd5-8a29ef94be23"
}
```

客户端只有 `requestId`，真实堆栈只存在于服务端日志。

`204 No Content` 和 `HEAD` 响应没有响应体，只保留 `X-Request-Id` 响应头；前端必须将它们作为无 body 的成功响应单独处理。

### 4.5 HTTP 状态和错误码分工

| 场景                 | HTTP 状态 | body code                      | 前端行为                                      |
| -------------------- | --------: | ------------------------------ | --------------------------------------------- |
| 缺少 Session Token   |       401 | `AUTH.SESSION_TOKEN_MISSING`   | 清理登录态并跳登录页                          |
| Session 失效         |       401 | `AUTH.SESSION_INVALID`         | 清理登录态并跳登录页                          |
| 账号或密码错误       |       422 | `AUTH.INVALID_CREDENTIALS`     | 留在登录页并显示错误，不触发 Session 过期跳转 |
| 无权限               |       403 | `AUTH.FORBIDDEN` 或模块错误码  | 提示无权限                                    |
| 参数错误             |       400 | `COMMON.VALIDATION_FAILED`     | 表单展示字段错误                              |
| 账号已存在           |       409 | `AUTH.ACCOUNT_ALREADY_EXISTS`  | 提示冲突                                      |
| 登录尝试过于频繁     |       429 | `AUTH.LOGIN_RATE_LIMITED`      | 提示稍后再试，遵守 `Retry-After`              |
| Redis/数据库暂不可用 |       503 | 模块级稳定错误码               | 提示稍后重试                                  |
| 未知程序错误         |       500 | `COMMON.INTERNAL_SERVER_ERROR` | 展示通用错误和 requestId                      |

这里把 JSON 登录接口的账号密码失败定义为 422：该公开接口本身不是一个等待 Bearer 凭据的受保护资源，不能返回一个不适用的 Bearer challenge。若未来改造成标准 OAuth 2.0 Token Endpoint，应按对应规范使用 `400 invalid_grant`；不要继续使用“401 但没有适用的 `WWW-Authenticate`”这种半标准状态。

## 5. 推荐改造顺序

先在项目根目录执行：

```powershell
vp install
```

确认依赖与锁文件一致后，再按以下顺序执行，不要一开始就批量替换所有异常：

1. 更新共享响应类型。
2. 配置 Fastify requestId。
3. 调整成功响应拦截器。
4. 创建 `AppException`。
5. 创建公共和认证错误目录。
6. 创建并注册 `GlobalExceptionFilter`。
7. 迁移 Guard 和 AuthService。
8. 迁移 Redis Session 异常并删除重复日志。
9. 修正启动错误边界。
10. 修正 React/Vue Axios 错误分支。
11. 增加自动化测试。
12. 构建 `shared + server`，再执行 `vp check` 和 workspace 测试。

全局 Filter 会保留旧 `HttpException` 的正确 HTTP 状态，但不会继续透传它的任意 message。迁移期间旧异常会临时收敛为 `COMMON.HTTP_<status>` 和通用安全文案，因此应优先迁移用户可见的认证模块。

## 7. 第二步：配置可信 requestId

Fastify 本身已经提供 `request.id`，当前项目不需要为了 HTTP requestId 单独引入 `nestjs-cls` 或 `uuid`。

修改：

```text
apps/server/src/main.ts
```

增加导入：

```ts
import { randomUUID } from 'node:crypto'
import { ConsoleLogger, Logger } from '@nestjs/common'
```

将 FastifyAdapter 改为：

```ts
new FastifyAdapter({
  trustProxy: ['127.0.0.1', '::1'],
  genReqId: () => randomUUID(),
})
```

不要直接写：

```ts
requestIdHeader: 'x-request-id'
```

Fastify 官方文档明确说明，启用 `requestIdHeader` 后调用方可以直接设置请求 ID，Fastify 不负责校验。未校验的值可能造成日志伪造、超长字段或追踪混乱。

如果以后必须接收网关传入的 request ID，应在 `genReqId` 中自己验证长度和字符集，并且只信任已配置的反向代理。W3C `traceparent`/traceId 属于 OpenTelemetry 链路上下文，不要与 requestId 混成同一个字段。

同时启用 NestJS 11 自带 JSON 日志，确保生产环境中的结构化错误元数据不会退化成难检索的纯文本：

```ts
const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter({
    trustProxy: ['127.0.0.1', '::1'],
    genReqId: () => randomUUID(),
  }),
  {
    logger: new ConsoleLogger({
      json: process.env.NODE_ENV === 'production',
      colors: process.env.NODE_ENV !== 'production',
    }),
  },
)
```

在 CORS 配置中加入：

```ts
exposedHeaders: ['X-Request-Id', 'WWW-Authenticate', 'Retry-After'],
```

浏览器因此可以读取响应头中的 requestId、401 challenge 和重试窗口。Filter 只为明确标记的 Session/Bearer 401 设置 `WWW-Authenticate: Bearer realm="api"`；JSON 账号密码登录失败使用 422，不冒充 Bearer challenge。429/503 的 `Retry-After` 应由真正知道重试窗口的限流器或依赖适配层设置，通用 Filter 不应猜测。

本阶段保证的是“HTTP 响应 ↔ HTTP 错误边界日志”的关联。Fastify 的 `request.id` 不会自动进入任意 Service/Repository 日志；如果后续要求所有内部日志都自动带 requestId，再通过 AsyncLocalStorage/`nestjs-cls` 或 request-aware logger 注入，不要误以为开启 JSON logger 就完成了上下文传播。

## 8. 第三步：让成功响应也携带 requestId

修改：

```text
apps/server/src/common/model/response.ts
```

完整替换为：

```ts
import { RESPONSE_SUCCESS_CODE, RESPONSE_SUCCESS_MSG } from '@/common/constants/response'

export class ResOp<T = unknown> {
  readonly code = RESPONSE_SUCCESS_CODE

  constructor(
    readonly data: T,
    readonly requestId: string,
    readonly message = RESPONSE_SUCCESS_MSG,
  ) {}
}
```

删除 `ResOp.error()`。失败不应作为普通返回值进入成功拦截器，而应抛异常交给 Filter。

修改：

```text
apps/server/src/common/interceptors/transform.ts
```

完整实现建议为：

```ts
import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common'
import { Reflector } from '@nestjs/core'
import type { FastifyReply, FastifyRequest } from 'fastify'
import { map } from 'rxjs'

import { BYPASS_KEY } from '../constants/decorator'
import { ResOp } from '../model/response'

@Injectable()
export class ResponseInterceptor<T> implements NestInterceptor<T> {
  constructor(private readonly reflector: Reflector) {}

  intercept(context: ExecutionContext, next: CallHandler<T>) {
    const http = context.switchToHttp()
    const request = http.getRequest<FastifyRequest>()
    const response = http.getResponse<FastifyReply>()

    response.header('x-request-id', request.id)

    const skip = this.reflector.getAllAndOverride<boolean>(BYPASS_KEY, [
      context.getHandler(),
      context.getClass(),
    ])

    if (skip) {
      return next.handle()
    }

    return next.handle().pipe(
      map((data) => {
        return new ResOp(data ?? null, request.id)
      }),
    )
  }
}
```

## 9. 第四步：创建类型安全的 AppException

新建：

```text
apps/server/src/common/exceptions/app.exception.ts
```

写入：

```ts
import { HttpException, type HttpStatus } from '@nestjs/common'
import type { ApiErrorDetail } from 'shared/types'

const APP_ERROR_CODE_PATTERN = /^[A-Z][A-Z0-9_]*(?:\.[A-Z][A-Z0-9_]*)+$/
const DETAIL_CODE_PATTERN = /^[A-Za-z][A-Za-z0-9._-]{0,79}$/

export interface AppErrorDefinition<Code extends string = string> {
  readonly code: Code
  readonly publicMessage: string
  readonly status: HttpStatus
  readonly bearerChallenge?: true
}

export interface AppExceptionOptions {
  readonly cause?: unknown
  readonly details?: readonly ApiErrorDetail[]
}

function normalizePublicText(value: unknown, maxLength: number): string {
  if (typeof value !== 'string') {
    return ''
  }

  return value
    .replace(/[\u0000-\u001F\u007F]/g, ' ')
    .trim()
    .slice(0, maxLength)
}

function normalizeDetails(
  details: readonly ApiErrorDetail[] | undefined,
): ApiErrorDetail[] | undefined {
  const normalized = details?.slice(0, 20).map((detail) => {
    const path = normalizePublicText(detail.path, 200)
    const code = DETAIL_CODE_PATTERN.test(detail.code) ? detail.code : 'INVALID_DETAIL'
    const message = normalizePublicText(detail.message, 200) || '请求内容无效'

    return {
      ...(path ? { path } : {}),
      code,
      message,
    }
  })

  return normalized?.length ? normalized : undefined
}

function assertErrorDefinition(definition: AppErrorDefinition): void {
  if (definition.code.length > 80 || !APP_ERROR_CODE_PATTERN.test(definition.code)) {
    throw new TypeError(`Invalid application error code: ${definition.code}`)
  }

  if (!Number.isInteger(definition.status) || definition.status < 400 || definition.status > 599) {
    throw new TypeError(`Application error status must be between 400 and 599`)
  }

  if (!normalizePublicText(definition.publicMessage, 300)) {
    throw new TypeError('Application error publicMessage must not be empty')
  }

  if (definition.bearerChallenge && definition.status !== 401) {
    throw new TypeError('bearerChallenge is only valid for HTTP 401 errors')
  }

  if (definition.status === 401 && !definition.bearerChallenge) {
    throw new TypeError('HTTP 401 errors must declare bearerChallenge')
  }
}

export class AppException<Code extends string = string> extends HttpException {
  readonly definition: AppErrorDefinition<Code>
  readonly code: Code
  readonly publicMessage: string
  readonly details?: readonly ApiErrorDetail[]

  constructor(definition: AppErrorDefinition<Code>, options: AppExceptionOptions = {}) {
    assertErrorDefinition(definition)

    const publicMessage = normalizePublicText(definition.publicMessage, 300)
    const normalizedDefinition = Object.freeze({ ...definition, publicMessage })
    const details = normalizeDetails(options.details)

    super(
      {
        code: definition.code,
        message: publicMessage,
        ...(details?.length ? { details } : {}),
      },
      definition.status,
      { cause: options.cause },
    )

    this.definition = normalizedDefinition
    this.code = definition.code
    this.publicMessage = publicMessage
    this.details = details
  }
}
```

这里把对外文案命名为 `publicMessage`，故意不提供任意 message 覆盖参数，并在运行时拒绝 2xx/3xx 状态和不符合命名规范的错误码。当前项目只使用 Bearer Session，因此所有 401 definition 都必须显式声明 `bearerChallenge: true`；反过来，该标记也只能用于 401。Filter 只生成固定、安全的 header，不让错误目录接受任意响应头字符串。

这样可以避免开发者误写：

```ts
throw new AppException(ERROR, { message: databaseError.message })
```

客户端文案应只来自经过审查的错误目录；真实异常放进 `cause`。TypeScript 无法阻止开发者强制类型转换或临时内联 definition，所以错误目录、代码审查和后面的唯一性测试仍是必要的安全边界。

## 11. 第六步：创建全局异常过滤器

新建：

```text
apps/server/src/common/filters/global-exception.filter.ts
```

写入：

```ts
import { AppException } from '@/common/exceptions/app.exception'
import { COMMON_ERRORS } from '@/common/exceptions/common.errors'
import {
  Catch,
  HttpException,
  HttpStatus,
  Injectable,
  Logger,
  type ArgumentsHost,
  type ExceptionFilter,
} from '@nestjs/common'
import { HttpAdapterHost } from '@nestjs/core'
import type { FastifyRequest } from 'fastify'
import { ZodSerializationException, ZodValidationException } from 'nestjs-zod'
import type { ApiErrorDetail, ApiFailure } from 'shared/types'
import { ZodError } from 'zod'

interface NormalizedException {
  readonly status: number
  readonly body: ApiFailure
  readonly bearerChallenge?: true
}

interface LoggedError {
  readonly name: string
  readonly message: string
  readonly stack?: string
}

@Catch()
@Injectable()
export class GlobalExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(GlobalExceptionFilter.name)

  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const context = host.switchToHttp()
    const request = context.getRequest<FastifyRequest>()
    const response = context.getResponse()
    const requestId = String(request.id)
    const normalized = this.normalize(exception, requestId)
    const { httpAdapter } = this.adapterHost

    this.writeLog(exception, normalized, request)

    if (httpAdapter.isHeadersSent(response)) {
      httpAdapter.end(response)
      return
    }

    httpAdapter.setHeader(response, 'x-request-id', requestId)

    if (normalized.bearerChallenge) {
      // RFC 9110：401 响应必须携带至少一个认证 challenge。
      httpAdapter.setHeader(response, 'www-authenticate', 'Bearer realm="api"')
    }

    httpAdapter.reply(response, normalized.body, normalized.status)
  }

  private normalize(exception: unknown, requestId: string): NormalizedException {
    if (exception instanceof ZodValidationException) {
      const details = this.getZodDetails(exception)

      return {
        status: COMMON_ERRORS.VALIDATION_FAILED.status,
        body: {
          code: COMMON_ERRORS.VALIDATION_FAILED.code,
          data: null,
          message: COMMON_ERRORS.VALIDATION_FAILED.publicMessage,
          requestId,
          ...(details?.length ? { details } : {}),
        },
      }
    }

    if (exception instanceof ZodSerializationException) {
      return this.createHttpFailure(HttpStatus.INTERNAL_SERVER_ERROR, requestId)
    }

    if (exception instanceof AppException) {
      return {
        status: exception.getStatus(),
        ...(exception.definition.bearerChallenge ? { bearerChallenge: true as const } : {}),
        body: {
          code: exception.code,
          data: null,
          message: exception.publicMessage,
          requestId,
          ...(exception.details?.length ? { details: [...exception.details] } : {}),
        },
      }
    }

    if (exception instanceof HttpException) {
      return this.normalizeHttpException(exception, requestId)
    }

    return this.createHttpFailure(HttpStatus.INTERNAL_SERVER_ERROR, requestId)
  }

  private normalizeHttpException(exception: HttpException, requestId: string): NormalizedException {
    const status = this.normalizeStatus(exception.getStatus())

    // 只有 AppException 的 publicMessage 被视为 client-safe。
    // 任意旧 HttpException（包括 4xx）只保留状态，不透传 message/response。
    // 迁移期仍可能遇到 Nest/Guard 直接抛出的旧式 401；本项目的 401 都代表
    // Bearer 保护资源，所以为它补上固定 challenge，避免违反 RFC 9110。
    return {
      ...this.createHttpFailure(status, requestId),
      ...(status === HttpStatus.UNAUTHORIZED ? { bearerChallenge: true as const } : {}),
    }
  }

  private getZodDetails(exception: ZodValidationException): ApiErrorDetail[] | undefined {
    const error = exception.getZodError()

    if (!(error instanceof ZodError)) {
      return undefined
    }

    return error.issues.slice(0, 20).map((issue) => {
      const path = this.normalizePublicText(
        issue.path.map((part) => String(part)).join('.'),
        '',
        200,
      )

      return {
        ...(path ? { path } : {}),
        code: issue.code,
        message: this.normalizePublicText(issue.message, '字段格式不正确', 200),
      }
    })
  }

  private createHttpFailure(status: number, requestId: string): NormalizedException {
    const safeStatus = this.normalizeStatus(status)
    const isInternalError = safeStatus === HttpStatus.INTERNAL_SERVER_ERROR

    return {
      status: safeStatus,
      body: {
        code: isInternalError
          ? COMMON_ERRORS.INTERNAL_SERVER_ERROR.code
          : `COMMON.HTTP_${safeStatus}`,
        data: null,
        message: isInternalError
          ? COMMON_ERRORS.INTERNAL_SERVER_ERROR.publicMessage
          : this.getHttpMessage(safeStatus),
        requestId,
      },
    }
  }

  private normalizeStatus(status: number): number {
    if (Number.isInteger(status) && status >= 400 && status <= 599) {
      return status
    }

    return HttpStatus.INTERNAL_SERVER_ERROR
  }

  private getHttpMessage(status: number): string {
    const messages: Partial<Record<number, string>> = {
      [HttpStatus.BAD_REQUEST]: '请求参数错误',
      [HttpStatus.UNAUTHORIZED]: '未登录或登录已失效',
      [HttpStatus.FORBIDDEN]: '无权限访问',
      [HttpStatus.NOT_FOUND]: '请求的资源不存在',
      [HttpStatus.METHOD_NOT_ALLOWED]: '请求方法不允许',
      [HttpStatus.CONFLICT]: '请求发生冲突',
      [HttpStatus.PAYLOAD_TOO_LARGE]: '请求内容过大',
      [HttpStatus.UNPROCESSABLE_ENTITY]: '请求内容无法处理',
      [HttpStatus.TOO_MANY_REQUESTS]: '请求过于频繁，请稍后重试',
      [HttpStatus.BAD_GATEWAY]: '上游服务异常',
      [HttpStatus.SERVICE_UNAVAILABLE]: '服务暂时不可用，请稍后重试',
      [HttpStatus.GATEWAY_TIMEOUT]: '上游服务响应超时',
    }

    return messages[status] ?? '请求失败'
  }

  private normalizePublicText(value: unknown, fallback: string, maxLength: number): string {
    if (typeof value !== 'string') {
      return fallback
    }

    const normalized = value
      .replace(/[\u0000-\u001F\u007F]/g, ' ')
      .trim()
      .slice(0, maxLength)

    return normalized || fallback
  }

  private writeLog(exception: unknown, normalized: NormalizedException, request: FastifyRequest) {
    const metadata = {
      event: 'http_request_failed',
      requestId: normalized.body.requestId,
      method: request.method,
      route: request.routeOptions?.url ?? '(unmatched)',
      status: normalized.status,
      code: normalized.body.code,
    }

    if (normalized.status >= HttpStatus.INTERNAL_SERVER_ERROR) {
      this.logger.error({
        ...metadata,
        errors: this.getErrorChain(exception),
      })
      return
    }

    // 预期的 400/401/404/409 不必全部写 warn，避免日志噪音。
    // 403 和 429 通常更值得进入安全或容量监控。
    if (
      normalized.status === HttpStatus.FORBIDDEN ||
      normalized.status === HttpStatus.TOO_MANY_REQUESTS
    ) {
      this.logger.warn(metadata)
    }
  }

  private getErrorChain(exception: unknown): LoggedError[] {
    const pending: unknown[] = [exception]

    // nestjs-zod 5.5 没有把响应序列化 ZodError 放进 cause，显式加入日志链。
    if (exception instanceof ZodSerializationException) {
      pending.push(exception.getZodError())
    }

    const visited = new Set<unknown>()
    const errors: LoggedError[] = []

    while (pending.length && errors.length < 8) {
      const current = pending.shift()

      if (!(current instanceof Error)) {
        if (current !== undefined && !visited.has(current)) {
          visited.add(current)
          errors.push({ name: 'NonErrorThrown', message: '非 Error 值已省略' })
        }
        continue
      }

      if (visited.has(current)) {
        continue
      }

      visited.add(current)

      // 只保留 V8 调用帧；message 和伪造的换行内容不会混入 stack。
      const stack = current.stack
        ?.split(/\r?\n/)
        .filter((line) => /^\s*at\s/.test(line))
        .slice(0, 30)
        .map((line) => this.redactLogText(line))
        .join('\n')
        .slice(0, 6000)

      errors.push({
        name: this.normalizePublicText(current.name, 'Error', 100),
        message: this.redactLogText(current.message),
        ...(stack ? { stack } : {}),
      })

      const cause = (current as Error & { cause?: unknown }).cause
      if (cause !== undefined) {
        pending.push(cause)
      }
    }

    return errors
  }

  private redactLogText(value: unknown): string {
    if (typeof value !== 'string') {
      return 'Error message unavailable'
    }

    return value
      .replace(/[\u0000-\u001F\u007F]/g, ' ')
      .replace(
        /\b(?:postgres(?:ql)?|mysql|redis(?:s)?|mongodb(?:\+srv)?|amqp(?:s)?|nats):\/\/[^\s,;]+/gi,
        '[REDACTED_CONNECTION_URI]',
      )
      .replace(
        /((?:password|passwd|token|authorization|cookie|api[-_]?key)["']?\s*[=:]\s*)(?:Bearer\s+)?[^\s,;]+/gi,
        '$1[REDACTED]',
      )
      .replace(/\bBearer\s+[^\s,;]+/gi, 'Bearer [REDACTED]')
      .replace(/([a-z][a-z0-9+.-]*:\/\/[^:\s/@]*:)[^@\s/]+@/gi, '$1[REDACTED]@')
      .trim()
      .slice(0, 1000)
  }
}
```

### 11.1 为什么未知 5xx 不读取 message

下面这些错误经常包含内部信息：

- PostgreSQL SQL、表名、字段名、约束名和连接信息。
- Redis 主机、端口、命令参数。
- 第三方接口 URL、响应正文和凭据。
- Zod 响应序列化时发现的内部数据结构。

只有经过错误目录审查的 `AppException` 可以向客户端暴露 5xx 安全文案；其他 5xx 一律使用通用文案。

### 11.2 为什么不记录请求 body

即使做字段脱敏，也容易漏掉：

```text
password
credentials.password
users[0].token
Authorization
cookie
自定义业务密钥字段
```

默认只记录 requestId、method、路由模板、HTTP status、业务 code 和经过限制/脱敏的错误链。路由模板避免把用户 ID、重置 Token 等路径参数写入日志，也避免指标高基数。确实需要审计的字段应使用独立的白名单审计日志，而不是在异常 Filter 中记录整个 body。

## 15. 数据库、Redis 和第三方错误应该在哪里映射

不要把所有驱动错误识别逻辑塞进全局 Filter。

正确位置是最了解业务语义的 Repository 或 Service 边界：

| 原始错误                                       | 映射建议                                    |
| ---------------------------------------------- | ------------------------------------------- |
| PostgreSQL `23505`，且确认是公开的唯一约束冲突 | HTTP 409 + 模块业务错误码                   |
| PostgreSQL `23503` 外键冲突                    | HTTP 409 + 模块业务错误码                   |
| PostgreSQL `40001` 序列化失败、`40P01` 死锁    | 仓储层有限重试，耗尽后 HTTP 503             |
| PostgreSQL 连接中断                            | HTTP 503，保留 cause                        |
| Redis 超时或连接失败                           | HTTP 503 + 模块级 `SERVICE_UNAVAILABLE`     |
| 第三方接口超时                                 | HTTP 504 或 503，取决于当前服务是否作为网关 |
| 第三方返回 4xx                                 | 不直接透传；转换成本系统定义的业务错误      |
| 无法识别的驱动错误                             | 不猜测状态，保留为未知 500                  |

当前注册接口已经使用：

```ts
.onConflictDoNothing({ target: users.account })
```

然后根据没有返回用户映射为 `AUTH.ACCOUNT_ALREADY_EXISTS`，这一做法可以保留。

## 16. 第十步：处理启动错误和非 HTTP 边界

全局 HTTP Filter 只能捕获进入 NestJS 请求生命周期的异常，捕获不到：

- 配置加载或应用启动失败。
- 后台任务、定时任务和队列消费者的未处理异常。
- 脱离请求生命周期的 Promise。
- WebSocket、GraphQL 和微服务传输层异常。

### 16.1 修正 bootstrap

当前文件末尾是：

```ts
void bootstrap()
```

前面 `main.ts` 的 `@nestjs/common` 导入中已经同时加入了 `Logger`。如果你分批操作，请合并到同一个 import，避免触发 `import/no-duplicates`：

```ts
import { ConsoleLogger, Logger } from '@nestjs/common'
```

再改为：

```ts
void bootstrap().catch((error: unknown) => {
  const logger = new Logger('Bootstrap')

  if (error instanceof Error) {
    logger.error(error.message, error.stack)
  } else {
    logger.error(String(error))
  }

  process.exit(1)
})
```

这里只在启动失败边界退出：部分初始化的 Redis/数据库连接可能仍持有事件循环，仅设置 `process.exitCode` 可能让失败进程一直不结束。当前 `ConsoleLogger` 是同步输出；如果以后换成带异步 transport 的 Pino 等 logger，应先显式 flush，再退出。

### 16.2 不要复制 nest-admin 的进程监听方式

不要在 Filter 构造器里写：

```ts
process.on('unhandledRejection', console.error)
process.on('uncaughtException', console.error)
```

未捕获异常后继续运行可能处于不一致状态。若部署环境需要自定义进程监听器，应在独立启动模块中记录、同步清理并终止，由 Docker、Kubernetes、PM2 或 systemd 重启。

### 16.3 其他传输层

- WebSocket 使用 `WsException` 和 WebSocket Exception Filter。
- 微服务使用 `RpcException` 和 RPC Filter。
- GraphQL 根据所用 driver 处理 GraphQL error extensions。
- 队列消费者在每个 job handler 的最外层做独立错误边界。

不要假设 HTTP Filter 能统一所有传输协议。

当前项目只有 HTTP，因此先用继承 `HttpException` 的 `AppException`，改造成本最低。如果未来同一领域错误要同时服务 REST、GraphQL、WebSocket 或队列，应把核心错误升级为不依赖 Nest HTTP 的 `AppError`，再由每种 transport presenter 映射状态和响应；不要让领域层直接操作 Express/Fastify Response。

### 17.1 增加三个响应辅助函数

放在 `getResponseData` 附近：

```ts
function getErrorResponse<RE>(error: unknown): RE | undefined {
  if (error === null || (typeof error !== 'object' && typeof error !== 'function')) {
    return undefined
  }

  return (error as { response?: RE }).response
}

function isBodylessResponse(status: number, method: unknown): boolean {
  const type = (method as { type?: unknown } | undefined)?.type
  return status === 204 || (typeof type === 'string' && type.toUpperCase() === 'HEAD')
}

function getErrorDisplayMessage(
  data: unknown,
  status: number,
  messageKey: string,
  defaultMessage: string,
): string {
  const message = getResponseMessage(data, messageKey, defaultMessage)

  if (status < 500) {
    return message
  }

  const requestId = getResponseField(data, 'requestId')
  if (typeof requestId !== 'string') {
    return message
  }

  const safeRequestId = requestId.replace(/[^A-Za-z0-9._-]/g, '').slice(0, 80)

  return safeRequestId ? `${message}（请求 ID：${safeRequestId}）` : message
}
```

### 17.2 给 Session 失效处理加 single-flight

先将 `BaseRequestOption` 中的回调类型改为：

```ts
unAuthorizedResponseFunc?: () => MaybePromise<void>
```

然后在 `createInstance()` 的 `const config = resolveConfig(option)` 后加入：

```ts
let unauthorizedTask: Promise<void> | undefined

function handleUnauthorizedOnce(): void {
  if (unauthorizedTask) {
    return
  }

  unauthorizedTask = Promise.resolve()
    .then(() => config.unAuthorizedResponseFunc?.())
    .then(() => undefined)
    .catch(() => undefined)
    .finally(() => {
      // 同一批并发请求只触发一次清理、跳转和 toast。
      setTimeout(() => {
        unauthorizedTask = undefined
      }, 1000)
    })
}
```

### 17.3 修正 onSuccess 中的 HTTP 分支

虽然 Axios 默认会把非 2xx 送入 `onError`，但 core 还支持 Fetch 或未来的 `validateStatus` 配置，所以 `onSuccess` 也要正确分流。

将原来的“只按 status 判断 401”改为：

```ts
const status = getResponseStatus(response)
const isSuccessStatus = isMatchedStatus(status, config.statusMap.success, response)
const bodyless = isBodylessResponse(status, method)

// 204 和 HEAD 都可能没有响应体；必须在 json()/text() 解析之前分流。
if (isSuccessStatus && bodyless) {
  if (showSuccess) {
    config.successMessageFunc?.(config.successDefaultMessage)
  }

  return undefined
}

// 非 2xx 的 HEAD 同样不读 body，但仍要走下面的失败分支。
const data = bodyless ? undefined : await getResponseData(response)

if (!isSuccessStatus) {
  const code = getResponseField(data, config.responseCodeKey)
  const isUnauthorizedStatus = isMatchedStatus(status, config.statusMap.unAuthorized, response)
  const isUnauthorizedCode =
    isUnauthorizedStatus &&
    code !== undefined &&
    Boolean(config.codeMap.unAuthorized?.length) &&
    isMatchedCode(code, config.codeMap.unAuthorized)

  if (isUnauthorizedCode) {
    handleUnauthorizedOnce()
  } else if (showError) {
    config.errorMessageFunc?.(
      getErrorDisplayMessage(data, status, config.responseMessageKey, config.errorDefaultMessage),
    )
  }

  return Promise.reject(response)
}
```

这样只有“HTTP 401，并且 code 是 Session 失效码”才会退出登录。伪造在 HTTP 400/500 中的同名 code 不会触发跳转；`AUTH.INVALID_CREDENTIALS` 使用 HTTP 422，只作为登录表单错误展示。`204` 与成功的 `HEAD` 会在调用 `getResponseData()` 前直接返回；失败的 `HEAD` 也不会尝试解析空 body，而是使用默认安全文案进入失败分支。

紧接着，把现有 wrapped 2xx 中 `if (!isMatchedCode(...))` 分支改成下面这样。新协议不再兼容“HTTP 200 + 错误业务码”，也不会在这个分支执行退出登录：

```ts
if (!isMatchedCode(code, config.codeMap.success)) {
  if (showError) {
    config.errorMessageFunc?.(
      getResponseMessage(data, config.responseMessageKey, config.errorDefaultMessage),
    )
  }

  return Promise.reject(response)
}
```

### 17.4 完整替换 onError

```ts
onError: async (error, method) => {
  const meta = getMethodMeta(method)
  const showError = getMetaFlag(meta, 'isShowErrorMessage', config.isShowErrorMessage)
  const response = getErrorResponse<RE>(error)

  if (response) {
    const status = getResponseStatus(response)
    const data = await getResponseData(response)
    const code = getResponseField(data, config.responseCodeKey)
    const isUnauthorizedStatus = isMatchedStatus(
      status,
      config.statusMap.unAuthorized,
      response,
    )
    const isUnauthorizedCode =
      isUnauthorizedStatus &&
      code !== undefined &&
      Boolean(config.codeMap.unAuthorized?.length) &&
      isMatchedCode(code, config.codeMap.unAuthorized)

    if (isUnauthorizedCode) {
      handleUnauthorizedOnce()
    } else if (showError) {
      config.errorMessageFunc?.(
        getErrorDisplayMessage(
          data,
          status,
          config.responseMessageKey,
          config.errorDefaultMessage,
        ),
      )
    }

    return Promise.reject(error)
  }

  if (showError) {
    config.errorMessageFunc?.(
      error instanceof Error && error.message ? error.message : config.errorDefaultMessage,
    )
  }

  return Promise.reject(error)
},
```

不要在 `unAuthorizedResponseFunc` 后再次调用普通 `errorMessageFunc`，否则一次 401 会出现两条提示。single-flight 还要增加并发测试，确保多个同时失效的请求只触发一次回调。

这类错误发生在任务进程创建阶段，不等同于代码编译错误；仍要查看每个子任务的真实输出。当前快照还必须先完成 17.8 的 `@bubblesjs/i18n-vue` 依赖声明，否则 Vue 构建会独立报 `TS2307`。

同时把根 `package.json` 的 `ready` 脚本改为先刷新 shared 声明，避免 CI 仍按旧顺序在 build 前 check：

```json
"ready": "vp run --filter shared build && vp check && vp run -r test && vp run -r build"
```

注意：

```text
apps/server/nest-cli.json -> compilerOptions.typeCheck = false
```

因此 Server 的 SWC 构建成功不代表 TypeScript 类型一定正确，`vp check` 不能省略。

当前调研快照本身已有无关基线问题：完整 `vp check` 先报告 86 个文件格式不一致；跳过格式的 `vp check --no-fmt` 还会报告 `packages/i18n/core` 的 2 个 `console` 类型错误，以及 `.agents/auth.config.ts` 空文件、React router unbound method 两个 warning；`web-vue` 还因缺失 `@bubblesjs/i18n-vue` 声明而报 `TS2307`，按 17.8 修正。改造前先保存这份基线，改造后要求“不新增问题”；不要为了本教程直接对全仓执行 `vp check --fix`，以免覆盖用户的无关文件。

## 20. 日志策略

推荐默认策略：

| 类型                  | 日志级别             | 是否记录 stack                | 是否记录 body |
| --------------------- | -------------------- | ----------------------------- | ------------- |
| 400 参数错误          | 默认不记或 debug     | 否                            | 否            |
| 401 登录/Session 错误 | 业务审计日志按需记录 | 否                            | 否            |
| 403 权限错误          | warn 或安全审计日志  | 否                            | 否            |
| 404                   | 默认不记             | 否                            | 否            |
| 409 业务冲突          | 默认不记             | 否                            | 否            |
| 429                   | warn/指标            | 否                            | 否            |
| 5xx                   | error                | 是，记录有限且脱敏的 cause 链 | 否            |

每条 5xx 日志至少包含：

```json
{
  "event": "http_request_failed",
  "requestId": "...",
  "method": "GET",
  "route": "/auth/me",
  "status": 503,
  "code": "AUTH.USER_SERVICE_UNAVAILABLE"
}
```

禁止默认记录：

- `Authorization`。
- Cookie。
- 密码、Session Token、API Key。
- 完整请求 body。
- 完整 query string。
- 数据库连接串。
- 第三方服务完整响应正文。

示例中的正则脱敏是最低防线，不可能识别所有业务秘密。生产日志平台仍应配置字段级脱敏和访问控制；应用代码禁止把凭据主动拼进 Error message。调用帧只保留形如 `at ...` 的行，避免攻击者用换行把伪造内容混入 stack。

## 21. 是否需要 RFC 9457

RFC 9457 是当前标准化 HTTP Problem Details 规范，典型格式为：

```json
{
  "type": "https://example.com/problems/auth/session-invalid",
  "title": "Authentication failed",
  "status": 401,
  "detail": "登录已失效，请重新登录",
  "instance": "urn:request:0dfad9bd-0de2-4552-bfd5-8a29ef94be23",
  "code": "AUTH.SESSION_INVALID",
  "requestId": "..."
}
```

如果以后 API 对外开放、需要跨团队 SDK 或 OpenAPI 客户端生成，可以迁移到 `application/problem+json`。其中 HTTP status 是权威状态；`type` 应是稳定、可文档化的问题类型 URI；`instance` 应唯一标识这一次问题（也可以省略），不能只填一个所有请求都相同的路由；`detail` 仍然只能包含安全公开信息。

当前阶段不建议立即切换，原因是：

- 两个前端已经依赖 `code/data/message`。
- 本项目是内部 monorepo，前后端同步发布。
- 本文方案已经保留真实 HTTP 状态和稳定业务错误码。

可以把 RFC 9457 作为 v2 API 协议，而不是在当前版本中混用两种错误结构。

## 22. 最终检查清单

- [ ] 成功响应只由 `ResponseInterceptor` 包装。
- [ ] 失败响应只由 `GlobalExceptionFilter` 包装。
- [ ] 使用 `APP_FILTER` 注册并保留依赖注入。
- [ ] Filter 使用 `HttpAdapterHost`，没有 Express 专用 `response.status().json()`。
- [ ] 业务失败使用真实 4xx/5xx，不返回 HTTP 200。
- [ ] 错误码是稳定的模块化字符串。
- [ ] 错误定义使用 `satisfies Record<string, AppErrorDefinition>` 做类型检查，并有全局唯一性测试。
- [ ] `AppException` 会在运行时拒绝非 400–599 状态和非法错误码。
- [ ] 任意旧式 4xx `HttpException` 也不会直接透传 message。
- [ ] 未知 5xx 不返回原始 message、stack 或 driver error。
- [ ] `ZodSerializationException` 被视为 500 且不泄漏响应数据。
- [ ] Zod 请求错误只返回安全、限量的 details。
- [ ] Fastify requestId 使用服务端生成的 UUID。
- [ ] 普通响应的响应头和响应体包含相同 requestId；204/HEAD 只检查响应头。
- [ ] Session/Bearer 401 包含 `WWW-Authenticate`；登录 422 不包含。
- [ ] 原始基础设施错误通过 `cause` 保留。
- [ ] 5xx 只在 HTTP 边界记录一次，有限 cause 链已脱敏。
- [ ] Filter 使用路由模板，不记录完整 headers、原始 URL、query 或 body。
- [ ] bootstrap Promise 有 `.catch()`。
- [ ] 没有在 Filter 构造器注册进程级异常监听器。
- [ ] React 和 Vue 的 `onError` 能读取 `error.response.data`。
- [ ] `responseMessageKey` 已统一为 `message`。
- [ ] React/Vue 成功 HTTP 状态包含 200、201、204，且 204/HEAD 不检查 body code。
- [ ] Session 失效 401 会清理登录态并 single-flight 跳转。
- [ ] `AUTH.INVALID_CREDENTIALS` 使用 422，且不会触发 Session 过期跳转。
- [ ] `web-vue` 已声明运行时依赖 `@bubblesjs/i18n-vue`，`vue-tsc` 不再被现有 TS2307 阻塞。
- [ ] 登录账号不存在时仍执行 dummy Argon2 verify，并配置了登录限流。
- [ ] 已执行 `vp run --filter shared build`，在类型检查前刷新 shared 声明。
- [ ] 已执行 `vp check`。
- [ ] 已执行 `vp run -r test`。
- [ ] 已执行 `vp run -r build`，覆盖 shared、Server、React 和 Vue。
