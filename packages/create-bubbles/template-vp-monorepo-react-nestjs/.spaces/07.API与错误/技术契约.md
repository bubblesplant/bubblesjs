# API 与统一错误技术契约

## 1. 状态和范围

- 状态：当前有效。
- 适用范围：Server HTTP API。
- 本契约不规定前端组件如何展示错误，也不把 OpenTelemetry Trace ID 作为当前请求关联标识。

NestJS 12 原生 Schema 迁移已在工作树实现：原生 Standard Schema 校验、响应处理与 Swagger 已接入，本契约的成功正文、失败结构、字段详情、安全和请求 ID 规则继续有效。范围见 [需求文档](./NestJS原生Schema迁移/需求文档.md)，操作见 [逐步实施教程](./NestJS原生Schema迁移/实施教程.md)，实际通过项及真实数据库／Redis／对象存储未覆盖边界见 [测试报告](./NestJS原生Schema迁移/测试报告.md)。

当前模板 Swagger 展示中文化已在工作树实现，范围与兼容边界见[接口文档中文化技术契约](./接口文档中文化/技术契约.md)。本次仅调整标题、描述、分组和操作摘要，中文覆盖与兼容比较、后端检查、类型、构建及 22 项回归通过，证据与未覆盖范围见[测试报告](./接口文档中文化/测试报告.md)，本契约的 HTTP 协议保持不变。

## 2. 成功响应

Server 成功响应直接返回业务正文，不增加通用 `{ code, data, message }` 外壳。

```json
{
  "id": "示例资源 ID",
  "name": "示例名称"
}
```

状态码按 HTTP 语义选择；调用方不得依赖成功正文中存在统一 `code` 字段。

## 3. 失败响应

所有可公开的 Server 失败响应统一为：

```ts
interface ApiErrorDetail {
  path?: string
  code: string
  message: string
}

interface ApiFailure {
  code: string
  message: string
  details?: ApiErrorDetail[]
}
```

示例：

```json
{
  "code": "COMMON.VALIDATION_FAILED",
  "message": "请求参数校验失败",
  "details": [
    {
      "path": "account",
      "code": "too_small",
      "message": "账号长度不符合要求"
    }
  ]
}
```

### 3.1 `details` 语义

- `details` 是通用业务错误详情，不限定为 Zod 校验格式。
- 每一项必须提供稳定 `code` 和可公开 `message`；`path` 仅在能够定位输入或业务字段时提供。
- 没有安全、有效详情时省略整个字段，不返回空数组占位。
- 详情数量、路径、错误码和公开文案必须限制长度并清理控制字符。

### 3.2 安全边界

- 5xx 不返回原始异常、堆栈、SQL、Redis／对象存储错误或内部连接信息。
- 业务异常只暴露登记过的公开文案；未知异常统一为内部错误。
- 日志中的 Authorization、Cookie、密码、Token、密钥、连接串和 URL 凭据必须脱敏。
- 401 是否返回 `WWW-Authenticate: Bearer` 由具体错误定义决定，不能仅凭 HTTP 状态盲目添加。

## 4. 请求关联 ID

- 每个 HTTP 响应通过响应头 `x-request-id` 返回当前请求关联 ID，包括成功和失败响应。
- 客户端反馈故障时应携带该响应头值，服务端日志使用同一 ID 定位请求。
- 当前 `x-request-id` 是应用请求 ID，不承诺等同于 OpenTelemetry Trace ID；以后接入链路追踪时可以建立映射，但不得静默改变现有字段语义。

## 5. 实现约束

- 新增、修改或重构后端接口前，按根目录 `AGENTS.md` 读取 [后端接口规则](../../.agents/rules/后端接口.md)，落实请求校验、访问策略、公开响应、数据一致性、Swagger 和验证要求；规则建立范围见 [需求文档](./后端接口规则/需求文档.md)。该执行入口不改变本契约的业务协议，也不代表所有历史接口已完成响应 Schema 迁移。
- 业务错误使用统一错误定义和 `AppException`，不能在各控制器随意返回不同 JSON 形状。
- 原生 Standard Schema Pipe 与保留的手动 Zod parse 均将请求校验错误转换为 `COMMON.VALIDATION_FAILED`，详情按统一规则规范化并保留可用的 issue code。
- 认证五个接口使用 `SerializeOptions({ schema })` 过滤公开响应字段，并通过 Swagger `standardSchema` 生成响应文档；响应校验失败进入安全的 500 分支。其他业务响应按既有公开字段契约继续运行，上传原始流不绑定 JSON 响应 Schema。
- Nest 遗留 `HttpException` 只映射固定公开文案，不直接透传异常消息。
- shared 只定义可供前后端复用的 `ApiFailure`／`ApiErrorDetail` 类型；Server 负责状态码、日志和安全清洗。

## 6. 验收标准

1. 任一成功接口直接返回业务正文。
2. 400～599 失败响应均符合 `{ code, message, details? }`。
3. `details` 可表达校验错误和其他业务错误，不绑定具体校验库。
4. 成功和失败响应都包含 `x-request-id`。
5. 未知 5xx 响应不泄露内部异常，服务端日志保留脱敏后的定位信息。
