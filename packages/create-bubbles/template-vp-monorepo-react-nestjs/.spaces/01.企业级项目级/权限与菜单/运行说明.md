## 首次使用

系统不创建默认密码，也不把第一个注册用户自动升级为管理员。

1. 使用已经单独审阅且不包含未获批准变更的数据库基线启动服务，在注册页创建自己的账号；当前完整迁移链的阻断与处置要求见“迁移与回退”。
2. 由持有服务端运行权限的部署人员执行 `access:init --account <已注册完整账号>`，指定首位平台管理员。命令使用服务端环境配置；账号必须有效。
3. 使用该账号登录，在工作空间入口进入平台管理。即使平台还没有企业，也保留平台入口。
4. 在企业管理中创建企业，通过全局账号选择器选择首位企业管理员。提交值为稳定 `userId`，平台自动建立该账号的企业成员关系并授予内置企业管理员角色。
5. 企业管理员进入企业空间，可直接注册新账号并加入企业。企业邀请是另一条已确认的产品入口，但对象、载体、有效期、接受、撤销和重发等规则尚未确认，当前不按本说明操作。创建项目时从本企业有效成员中选择首位项目管理员，并提交 `administratorUserId`。
6. 项目管理员从所属企业的有效成员候选中添加项目成员；候选排除已经加入当前项目的成员，表单提交 `userId`，服务端再次校验企业成员资格、状态和重复关系。

普通公开注册账号尚未加入企业时，工作空间可提示联系企业管理员。邀请如何生成、传递和接受仍待产品确认，不能把当前接受页当作正式操作入口。公开注册不会自动创建企业、项目或分配管理权限；企业“直接注册成员”只用于创建新账号，不能覆盖或重复创建既有平台账号，也不能要求用户提供完整账号让管理员直接挂接。

登录后或访问默认入口 `/`、`/home` 时，只有一个项目且没有平台或额外企业管理职责的成员直接进入项目。多项目、平台身份、企业管理员及拥有额外企业权限的成员进入工作空间选择页。项目内的“切换空间”始终打开选择页；主动访问具体企业或项目链接时保留目标。

初始化命令重复指定原账号只同步系统功能目录；指定其他账号会被拒绝。后续平台管理员通过已有平台管理员分配角色，不能用初始化命令重复提权。已被撤销的用户角色不会通过重复初始化恢复。

## 日常管理

- 平台管理员管理企业开通、启停和企业管理员设置。平台身份本身不提供企业内部业务访问权。
- 企业管理员管理本企业全部项目，无需额外加入项目。创建项目必须是有效内置企业管理员，不能通过自定义角色下放。
- 企业邀请只确认入口，当前按钮禁用并提示流程待确认；旧邀请列表、链接、撤销、重发和接受页面已撤下。协议确认前不提供邀请业务操作。
- 项目管理员只管理当前项目；项目成员必须先是所属企业成员。
- 停用保留关系和授权；恢复只恢复当前对象自身状态。移除企业成员会同时清理企业角色以及下属项目成员关系、项目角色，再加入只获得默认成员角色。
- 平台禁用企业最后一个管理员账号后，由平台设置或更换企业管理员。停用中的企业也可补任，补任不会自动启用企业。
- 更换管理员时选择新账号及要替换的旧任。旧任保留成员关系和其他角色，撤销的管理员角色不会在账号重新启用后恢复。
- 系统始终保护最后一个有效平台管理员。账号重新启用后需要重新登录，旧会话不会恢复。

资料、成员、角色和菜单的编辑使用版本号检测并发修改。遇到版本冲突，重新加载当前数据后再提交，不直接覆盖他人的更改。

## 菜单与功能发布

平台统一配置平台、企业、项目三套菜单树。名称、图标、排序、隐藏、启停及合法父级可调整；页面编号和操作权限来自代码功能目录，菜单编辑不能创建尚未开发的页面代码。

隐藏只影响导航，已获授权的人仍可直接访问。停用会同时阻断页面、按钮、接口及下级功能，内置管理员也不能绕过。平台企业、账号、角色和菜单等恢复管理入口及其祖先受到保护。

新功能发布后，系统补齐对应内置管理员权限；普通成员、自定义角色和已有用户角色分配不会自动扩大。种子更新保留菜单配置。旧前端过滤未知页面和空目录，加载含新页面代码的新版前端后才显示新入口。

## 废弃权限清理

第一版功能目录没有废弃项时，预览为空属于正常状态，无需执行清理。功能停用、服务版本暂时找不到某个权限或旧前端不认识页面，都不是废弃依据。

清理前先将目标权限在代码功能目录中明确标记废弃，并完成目标功能下线。部署人员核对全部在用服务实例及权限依赖，生成受控的只读 JSON 证明文件，通过 `ACCESS_DEPLOYMENT_PROOF_FILE` 提供给服务端。文件格式见 [技术契约](./技术契约.md) 第 8 节。

证明包含部署标识、核验时间、过期时间、各服务版本、实例清单和所依赖权限。当前服务版本及依赖必须匹配，证明有效期不超过 24 小时。切换实例、重新发布或回滚之前先撤销旧证明，完成核验后重新生成。文件由运维流程保障真实与完整，系统不会自动发现实际部署实例。

平台管理员先预览影响范围，再执行清理。服务端在事务锁内重新核对证明、候选项、引用和受保护节点；存在阻断项则拒绝整次操作。通过后清理授权引用、菜单及权限，更新版本、写清理记录和审计。重复清理不会再次删除，后续初始化也不会重建已清理权限。

## 迁移与回退

部署顺序为：备份数据库 → 停止旧版本服务 → 审阅预检与版本兼容性 → 执行 `db:migrate` → 发布新服务并同步目录 → 发布前端。`0006` 遇到非空企业父子关系、已存在邀请表、旧层级菜单有子项或其他权限引用时整批中止，须先另行审阅数据处理方案；不自动清空业务数据，不修改已应用历史，不使用 `db:push` 绕过。

当前数据库已应用 `0003`，本轮未执行 `0006`。已应用的 `0003` SQL／快照保留历史一致性；未应用的 `0004` 已撤下并不可执行归档，独立 `0005` 保留，新增 `0006` 前向收口。有效 journal 顺序为 `0000 → 0001 → 0002 → 0003 → 0005 → 0006`。新环境按有效 journal 完整执行；尚未应用 0003 的存量库仍受历史预检约束。执行步骤见[数据库操作指南](../../05.运行维护/数据库迁移/操作指南.md)。

迁移失败时停止后续发布，先核实数据库事务回滚结果；需要恢复时使用经过核验的备份。已开始写入新模型数据后，不直接删除新增表或倒退迁移。应用回滚之前检查旧版本是否兼容当前数据库，并撤销当前废弃权限清理证明。

现有账号保持原登录方式，不自动归入任何企业。上传继续使用原 `ownerId` 授权，本期没有将旧上传猜测归属到默认企业。

## 启动命令

以下命令从工程根目录执行。先配置目标环境的数据库、Redis、对象存储和会话密钥。所有服务端命令使用相同的 `NODE_ENV` 和环境配置。环境文件按 `.env.<NODE_ENV>.local`、`.env.local`、`.env.<NODE_ENV>`、`.env` 顺序加载；未指定 `NODE_ENV` 时为 `development`。

构建共享包及前后端：

```powershell
vp run --filter shared build
vp run --filter server build
vp run --filter web build
```

确认目标数据库已按正式操作指南迁移至当前模型后，在后端目录启动服务：

```powershell
Set-Location apps/server
node dist/src/main.js
```

另开一个终端，在前端目录运行开发页面；API 地址应指向实际后端，下面端口与本次隔离验收一致：

```powershell
Set-Location apps/web
$env:VITE_API_URL = 'http://127.0.0.1:3301'
$env:VITE_API_AFFIX = '/api'
$env:VITE_PORT = '5301'
vp dev --mode dev --host 127.0.0.1 --port 5301 --strictPort
```

在页面注册自己的账号后，由部署人员在另一个终端的 `apps/server` 目录执行初始化，将示例账号替换为已经注册的完整账号：

```powershell
node dist/src/access-init.js --account your_registered_account
```

也可在该目录运行源码脚本 `vp run access:init -- --account your_registered_account`。初始化后重新进入工作空间，即可看到平台管理入口。服务启动会同步功能目录，普通启动不会自动创建平台管理员。

以上基础构建产物启动和初始化是历史隔离记录；2026-10-14 P0 迁移与代码专项另有[交付证据](../组织架构/交付记录.md)，不能将其写成当前环境部署已完成。隔离验收配置由运行期注入，未代替用户迁移当前数据库。
