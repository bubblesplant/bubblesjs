## 1. 工程基线与实施边界

- 继续使用现有 `platform | company | project` 三种 `AccessScope`。平台下企业彼此独立，不新增企业类型或企业间父子关系；集团、事业群、分公司、部门等层级名称由单个企业内部的组织单元表达，不新增 group、organization 或 department 作用域。
- 共享 DTO、返回类型、枚举、权限目录和纯规范化方法统一放在 `packages/shared/src/types`、`packages/shared/src/utils` 并从既有入口导出；前端和后端不得复制第二份传输类型。
- 成功响应直接返回约定 JSON，不增加 `{ code, data }` 包装。失败沿用 `ApiFailure = { code, message, details? }`，并使用服务端 `request.id`／`x-request-id` 关联审计。
- GET 成功为 200，创建资源的 POST 成功为 201，其余写操作成功为 200。稳定资源没有 DELETE 端点；批量替换关系直接返回替换后的关系集合。
- Controller 接收 `unknown`，使用 Zod `strictObject` 拒绝未知字段；URL UUID 使用现有路由校验；作用域只从 URL 和登录上下文推导，不能相信请求体自报的 companyId、projectId 或 scope。
- 所有新增 Controller 显式声明 `@AccessPolicy`，未声明策略继续默认拒绝。鉴权顺序固定为登录与账号状态 → 作用域与成员资格 → 页面及操作权限 → 资源归属。
- 跨企业、跨项目、跨组织树 ID 与不存在 ID 统一返回 404；已确认处于当前作用域但缺少权限返回 403。
- 前端继续使用现有 alova 实例、页面旁 `api.ts`、React Router middleware、工作空间取消控制和 `cacheFor: 0, shareRequest: false` 的管理请求约定。
- 本期实现范围只包含 React Web、NestJS Server 和 shared；不改 `apps/web-vue`，不实现完整工作流。

## 2. 共享类型与字段规范

### 2.1 基础枚举与引用

```ts
type OrganizationScope = Extract<AccessScope, { type: 'company' | 'project' }>
type OrganizationDuty = 'member' | 'leader' | 'deputy'
type ProjectOrganizationInitialization =
  { mode: 'blank' } | { mode: 'template'; templateId: string; templateVersion: number }

interface OrganizationRelationInput {
  organizationUnitId: string
  duty: OrganizationDuty
}
```

- 所有实体 ID 和 userId 均为 UUID 字符串；日期输出 ISO 8601 UTC 字符串。
- `sort` 是 `0～999999999` 的单个整数，不拆分主排序／细分排序，不接受小数。
- 所有稳定可编辑资源的 `version` 从 1 开始；写请求携带 `expectedVersion`，成功后版本加一。
- 名称等展示文本保存前只 `trim` 并保留大小写；需要唯一校验的名称和编码统一使用 `lower(NFKC(trim(value)))` 作为规范值，内部空白不折叠。所有公开 code DTO 先 trim 并按 ASCII 大小写字母／数字／下划线／短横线校验，再执行 `toLowerCase` 保存；因此新建或更新写入的 code 及其响应固定为小写，未被编辑的存量记录仍按原值展示，迁移不静默重写。新增表的 key 列由共享纯方法计算并写入，数据库再以 `lower(normalize(btrim(value), NFKC))` CHECK 校验原值与 key 一致；没有 key 列的既有 code 使用同一表达式函数索引，不能假设 PostgreSQL `lower()` 自动完成 NFKC。
- 公共规范化方法、树深度计算、作用域 URL 构造等非显然方法必须写 JSDoc；超过 3 个参数的方法使用对象参数。

### 2.2 字段长度、格式与分页基线

| 字段          | 共享 DTO 规则                                             | 新表数据库规则                              |
| ------------- | --------------------------------------------------------- | ------------------------------------------- |
| `name`        | `trim` 后 2～100 个字符                                   | `varchar(100)`，并以 CHECK 保证长度下限     |
| `code`        | trim 后 2～32 个字符，先接受 `^[A-Za-z0-9_-]+$`，再转小写 | `varchar(32)`，CHECK 保证长度、字符集和小写 |
| `description` | 可省略；`trim` 后 0～500 个字符，省略时保存为空字符串     | `varchar(500)`，默认空字符串                |
| `query`       | 可省略；`trim` 后最多 100 个字符                          | 不持久化                                    |
| `page`        | 正整数，默认 1                                            | 不持久化                                    |
| `pageSize`    | 1～100 的整数，默认 20                                    | 不持久化                                    |

- 上表的 `name`、`code`、`description` 统一适用于企业、项目、组织单元、岗位、组织模板及模板子项；shared 导出唯一一套基础 schema，各 Controller 组合复用，不得在前后端或模块内复制不同上限。
- 新增业务表的物理列宽与公开 DTO 上限一致。既有 `companies.name varchar(100)` 保持不变；既有 `companies.description/projects.description` 可继续使用 `text`，但公开写接口仍严格执行 500 字上限。
- 既有 `companies.code` 与 `projects.code` 当前为 `varchar(64)`，本期不缩短物理列，避免无意义重写和失败回滚；所有新旧公开写接口仍统一执行 32 字上限，不得因物理容量为 64 而放宽 API。
- migration 在任何 DDL 前预检存量企业和项目 code。只要 trim 后长度不在 2～32、字符不符合大小写 ASCII 字母／数字／下划线／短横线规则，或新规范键产生冲突，就立即停止迁移并输出记录 ID 供人工修复；禁止自动截断、改名、拼接后缀或静默转小写。存量 code 保留原展示值但参与不区分大小写的规范唯一校验；后续公开写入统一保存小写。企业 code 继续保持既有全局唯一，项目 code 继续保持企业内唯一。
- 所有数组筛选字段和 resolve 的 `userIds` 每类最多 100 个 UUID；字段一旦出现就必须至少 1 个且去重，空数组和重复项按请求校验失败处理。

```ts
interface CreateCompanyRequest {
```

- 平台继续使用既有企业列表管理彼此独立的企业，不新增企业树查询、父级选择、企业移动或层级摘要端点。
- 项目始终直接保存一个 `companyId`；组织树、岗位、成员、模板及权限校验均以该直接所属企业为边界，不产生跨企业继承或隐式归属。

### 2.4 组织树与组织单元

```ts
interface OrganizationTreeRecord {
  id: string
  scope: OrganizationScope
  parentId: string | null
  units: OrganizationUnitNode[]
}

interface OrganizationTreeQuery {
  parentId?: string
}

interface OrganizationUnitRecord {
  id: string
  treeId: string
  parentId: string | null
  name: string
  code: string
  description: string
  sort: number
  status: EntityStatus
  version: number
  depth: number
  fullPath: string
  createdAt: string
  updatedAt: string
}

interface OrganizationUnitNode extends OrganizationUnitRecord {
  effective: boolean
  hasChildren: boolean
}

interface CreateOrganizationUnitRequest {
  parentId?: string | null
  name: string
  code: string
  description?: string
  sort?: number
}

interface UpdateOrganizationUnitRequest extends VersionRequest {
  name?: string
  code?: string
  description?: string
  sort?: number
}

interface MoveOrganizationUnitRequest extends VersionRequest {
  parentId: string | null
  sort?: number
}
```

- 企业／项目本身只作为 UI 虚拟根，不持久化根节点；真实顶级节点 `parentId = null` 且深度为 1。
- 树接口按父节点懒加载：查询省略 `parentId` 时返回顶级节点并在响应中写 `parentId = null`；传入 `parentId` 时只返回其直接子节点。每个节点以 `hasChildren` 表示是否还有可见直接子节点，不递归返回 `children`。
- 每棵树最多 10 层。创建、移动和模板复制都在事务锁内校验目标节点及完整子树深度。
- `code` 在单棵树内规范化唯一；`name` 在同一父级下规范化唯一，不同分支允许同名。
- `fullPath`、`depth`、`effective` 是查询派生字段，不落库。`effective` 仅在自身及全部祖先都 active 时为 true。
- 停用节点不改写后代状态，也不删除成员关系；停用父节点下不能新建节点，有无效祖先的节点不能成为有效节点的移动目标。
- 移动保持组织单元 ID 不变，禁止移动到自身或后代。未传 sort 时取目标同级下一个可用整数。

### 2.5 组织成员关系

```ts
interface OrganizationMembershipRecord {
  id: string
  organizationUnit: Pick<OrganizationUnitRecord, 'id' | 'name' | 'code' | 'fullPath' | 'status'>
  duty: OrganizationDuty
  createdAt: string
  updatedAt: string
}

interface ReplaceMemberOrganizationUnitsRequest {
  relations: OrganizationRelationInput[]
}

interface ReplaceMemberOrganizationUnitsResult {
  userId: string
  relations: OrganizationMembershipRecord[]
}

interface OrganizationUnitMemberInput {
  userId: string
  duty: OrganizationDuty
}

interface OrganizationUnitMemberRecord {
  membershipId: string
  member: Pick<MemberRecord, 'id' | 'userId' | 'account' | 'name' | 'status' | 'accountStatus'>
  duty: OrganizationDuty
  createdAt: string
  updatedAt: string
}

interface ReplaceOrganizationUnitMembersRequest {
  members: OrganizationUnitMemberInput[]
}

interface ReplaceOrganizationUnitMembersResult {
  organizationUnitId: string
  members: OrganizationUnitMemberRecord[]
}
```

- 企业关系绑定既有 company member，项目关系绑定既有 project member。一次请求中的 `userId` 与所有组织单元必须属于 URL 指定的同一作用域。
- 同一成员可加入多个组织单元；`(成员, 组织单元)` 唯一。全部关系同等，不存在主归属、默认组织或数组第一项的特殊语义。
- 每条关系只有一个 duty；每个组织单元最多一个 leader、可有多个 deputy。同一个人可以领导多个组织单元。
- 按成员替换时，`relations` 是该成员在当前 URL 作用域内的完整组织关系集合；按组织单元替换时，`members` 是该单元的完整成员集合，只替换该单元关系并保留每名成员在其他组织单元的关系。两种方向都在锁内原子完成，重复组织单元／userId、跨作用域、非法新增／升级或负责人冲突使整批失败，不能留下部分写入。
- 两种替换请求的空数组都允许：按成员空数组解除该成员全部组织关系，按组织单元空数组清空该单元全部成员。按组织单元提交时同样比较该单元的持久化旧集合与新集合；停用成员或停用／无效组织单元的旧关系只可原样保留、移除或降级，不可新增或升级，且最终最多一名 leader。
- 关系返回固定按 leader、deputy、member，再按关系 ID 升序。不存在成员排序字段。
- “未归属组织”由候选查询的 `unassigned = true` 派生，数据库不创建对应节点。
- active 成员只可向 effective 组织单元新增关系或升级职责。停用成员以及指向停用／无效组织单元的既有关系可原样保留、移除，或按 `leader → deputy → member` 的方向降级；不得新增关系或反向升级职责。服务端比较持久化旧集合与请求新集合后判定，而不是把含停用 ID 的请求一律拒绝。

- 岗位是企业或项目作用域内的平面列表，不是树，不属于组织单元。

- 同一作用域的岗位 name 和 code 分别按规范键唯一；一人可多岗，一岗可多人，成员与岗位组合唯一。
- 组织关系、岗位任职和 RBAC 角色分别维护、分别审计，任一方变化不得联动另外两方。
- 按成员替换时，`positionIds` 是该成员在当前 URL 作用域内的完整岗位集合；按岗位替换时，`userIds` 是该岗位的完整成员集合，只替换该岗位任职并保留每名成员的其他岗位。两种方向均在锁内原子完成，重复 ID、跨作用域或非法新增使整批失败。
- 两种岗位替换请求的空数组都允许，分别表示解除该成员全部任职或清空该岗位全部任职。停用成员或停用岗位的既有任职可原样保留或移除，但不得新增；服务端必须比较旧集合和新集合，不能因目标停用而阻止清理，也不能借全量替换新增停用关系。

- `clientKey` 只用于一次请求内表达模板树父子关系，不持久化，不作为跨请求稳定 ID；同一请求内唯一且 `parentClientKey` 必须引用本请求节点。缺失父节点、自引用或任意环按 400 `COMMON.VALIDATION_FAILED` 拒绝；形成的森林超过 10 层按 409 `ACCESS.ORGANIZATION_DEPTH_EXCEEDED` 拒绝。
- 模板 `version` 同时是乐观锁版本和当前组织单元／岗位子项快照版本，不代表可重建整个模板聚合的历史。创建时 `isDefault` 省略即为 false；模板 PUT 必须显式提交 `isDefault` 与完整定义，更新模板主表当前值并生成下一份完整子项版本快照；状态 PATCH 的 `status/isDefault` 至少提交一项，省略的字段保持原值，也必须生成下一版本，并把上一版本的全部组织单元和岗位原样复制到新版本后再变更状态／默认标记，不能产生没有子项的当前版本。旧版本子项永久保留供来源追踪和审计，不作为新项目可选版本；旧的 name、description、status、isDefault 只由审计记录表达，不承诺从模板表重建历史主表状态。
- 每个企业最多一个 active 且 `isDefault = true` 的模板。设为默认时目标最终状态必须为 active；同一事务锁定目标和旧默认模板。若存在另一旧默认模板，旧模板也递增 version、把自身当前完整子项复制到下一版本、仅把 `isDefault` 改为 false，并写独立审计；不能旁路 UPDATE 绕过乐观锁或生成空版本。停用默认模板时目标新版本强制 `isDefault = false`，不自动挑选替代默认模板。
- 项目创建必须显式提交 `organizationInitialization`。blank 不允许模板字段；template 必须提交 templateId 和 templateVersion，且模板属于项目直接企业、active、版本等于当前版本。
- 模板查询先以项目直接 `companyId + templateId` 约束资源归属；跨企业或不存在统一 404。只有已经确认属于当前企业后，停用、不能作为默认或其他当前作用域内不可用状态才返回 422 `ACCESS.TEMPLATE_UNAVAILABLE`，版本不等于当前版本返回 409 `ACCESS.TEMPLATE_VERSION_CONFLICT`。
- template 初始化在写锁内先比较 `organization_templates.version`，再只读取 `organization_template_units/positions` 中该 `template_id + template_version` 的完整子项版本快照；不能读取“最新子项”或跨版本拼接。状态变更生成的新版本因已复制完整子项，可被后续项目正常初始化。
- 模板组织单元输入和表有意不含 status：模板中存在的结构节点都可用，初始化后的项目组织单元统一为 active，避免在模板树中再引入无效祖先语义。模板岗位是平面定义，保留显式 status；初始化时按原状态复制，disabled 岗位在项目中仍为 disabled，项目可随后独立启用。因此 97 个新增字段统计不变，此差异不是漏字段。
- 模板复制只生成项目组织单元和项目岗位，保留各自来源模板子项 ID；不复制成员、负责人、组织关系、岗位任职或 RBAC 角色。
- 项目创建后组织和岗位完全独立；模板修改、停用、恢复均不自动同步既有项目。

### 2.8 账号与组织成员候选


- `OrganizationMemberSelector` 的稳定选择值固定为 `userId`。当前企业／项目由调用候选及保存动作的 URL `AccessScope` 解释；候选中的项目 identity 只用于权限裁剪后的展示、筛选与辨识，不进入持久化选择值。需要修改某个项目的关系时，业务必须在该项目 URL 下提交，不能让客户端在请求体中自报 scope。
- `organizationUnits` 中每个标签对应一条真实成员关系，必须返回稳定的 `membershipId` 与 `duty`。`browseOrganization` 的 `organizationUnitIds` 恰好包含一个 ID 时，改按该匹配关系的 duty 优先级 `leader → deputy → member`、`membershipId ASC`、`userId ASC` 排序，使组织成员表可直接分页编辑；其他候选查询仍按规范化姓名、完整账号、userId 排序。

- 普通浏览时，企业端点聚合当前企业身份及调用者在该企业内获准查看的项目身份；项目端点只返回当前项目身份。企业端只有具备 `company.projects.read` 时才可读取任何项目 identity，并继续按现有项目可见性逐项目裁剪；仅有 `company.projects.read` 不代表可以读取项目组织、岗位或角色标签。企业端未传 `projectIds` 时，身份筛选域是当前企业身份；传入时筛选域是所列可见项目身份，`projectIds` 内部为 OR，且当前企业身份不参与本次筛选。项目端不接受 `projectIds`。
- 企业端返回的每个项目 identity 都按该项目实际权限裁剪：组织标签要求该项目的 `project.organization.read`，岗位标签要求 `project.positions.read`，角色标签要求既有 `project.roles.read`；缺少某类权限时不返回该类标签，不能用其他项目或企业权限替代。`organizationUnitIds`、`positionIds`、`roleIds` 用于项目身份筛选时，也必须对每个目标项目分别具备上述对应权限；可见项目内权限不足返回 403，不可见、跨企业或不存在的项目／资源返回 404。
- `organizationUnitIds`、`positionIds`、`roleIds` 各自数组内部为 OR，不同类别之间与 `query`、`unassigned` 之间为 AND；必须由同一个筛选域 identity 同时满足全部身份类条件，不能用企业身份的角色与项目身份的组织标签拼成一次命中。候选只要存在一个这样的 identity 即命中。
- `unassigned` 省略或为 `false` 时不参与过滤；为 `true` 时要求上述同一个 identity 没有任何持久化组织关系，包含指向停用组织单元的关系也仍算“已归属”。因此企业端无 `projectIds` 时判断企业组织关系，有 `projectIds` 时分别在所选项目身份中判断；项目端只判断当前项目。
- 所有筛选 ID 必须属于本次筛选域且对调用者可见；跨域或不存在返回 404，筛选能力所需权限不足返回 403。响应中的 identities 及各类标签仍按当前企业或逐项目权限返回，不能借筛选参数扩张可见范围。
- 同一候选存在多个命中 identity 时，只要至少一个 identity 在当前 purpose 下可提交，候选整体 `disabled=false`；全部不可提交时，才按 `accountInactive → scopeInactive → memberInactive → organizationInactive → positionInactive` 取第一个禁选原因。后两项只在本次命中依赖对应无效标签时生效；某人存在其他无效组织或岗位标签，不会使其有效身份无条件禁选。提交业务动作时服务端按该动作重新校验，不能信任查询时状态。
- `assignPositionMembers` 只返回 URL 当前企业或项目的成员身份，要求对应 `*.positions.read` 与 `*.positions.assign`，不要求 `*.organization.read`。该 purpose 只接受 `page/pageSize/query/positionIds/includeDisabled`；响应保留当前身份的岗位标签，并清空组织与角色标签，既满足岗位成员回显和筛选，也不借岗位维护权限暴露组织信息。
- `createProjectAdministrator` 与 `setProjectAdministrator` 只允许调用企业端候选接口，分别要求既有 `company.projects.create` 与 `company.projects.administrator`，不额外要求 `company.organization.read` 或 `company.members.read`。这两个 purpose 只允许 `page/pageSize/query/includeDisabled`，其他身份筛选字段出现即 400；只搜索当前企业成员，并把 identities 裁成一个企业身份且清空组织、岗位、角色标签，避免为选管理员扩大信息暴露。
- `addProjectMember` 只允许调用项目端候选接口，要求 `project.members.add`，不额外要求企业成员列表、组织、岗位或角色读取权限。该 purpose 只接受 `page/pageSize/query/includeDisabled`；只返回项目所属企业中账号和企业成员关系均有效、且尚无当前项目成员关系的用户，identity 只保留所属企业成员摘要并清空组织、岗位、角色标签。resolve 对已经加入项目或状态失效的既有选择仍返回禁选原因，保存接口仍须二次校验。

- 项目普通成员新增提交 `{ userId }`。后端在写事务中重新验证账号 active、目标是当前项目所属企业的 active company member、当前项目不存在该成员关系；不满足时返回 `ACCESS.INVALID_MEMBER_RELATION`，重复关系按 `ACCESS.DUPLICATE_RESOURCE` 处理。候选结果不构成写入授权。

### 3.2 关系完整性与生命周期

- `organization_trees`、`organization_units`、`positions`、`organization_templates` 及模板版本子项使用 RESTRICT，不通过级联物理删除稳定资源。
- 成员关系表对现有 company/project member 使用 `ON DELETE CASCADE` 仅作数据库兜底；正式成员移除必须先在同一业务事务显式删除组织关系、负责人关系和岗位任职并写审计，再删除成员，不能依赖静默级联代替审计。
- 每张关系表复制必要 scope 键并使用组合 FK。禁止只分别 FK `memberId` 与 `unitId/positionId`，否则数据库会允许跨企业或跨项目组合。
- `organization_trees` 的 CHECK 精确固定两种行形状：company 行为 `scope_type='company' AND company_id IS NOT NULL AND project_id IS NULL`；project 行为 `scope_type='project' AND company_id IS NOT NULL AND project_id IS NOT NULL`。project 行另以 `(company_id,project_id)` 引用既有 `projects(company_id,id)`。
- `organization_trees` 同时建立 `UNIQUE(id,scope_type,company_id)` 与 `UNIQUE(id,scope_type,company_id,project_id)`；前者只供企业关系引用，后者只供 project_id 非空的项目关系引用。每企业一棵树使用 company 条件唯一索引，每项目一棵树使用 project 条件唯一索引。
- 企业组织关系表不包含 nullable `project_id`，且 `scope_type/company_id/tree_id/organization_unit_id/user_id` 全部 NOT NULL；分别以 `(tree_id,scope_type,company_id)`、`(tree_id,organization_unit_id)`、`(company_id,user_id)` 引用企业树、组织单元和 company member。
- 项目组织关系表的 `scope_type/company_id/project_id/tree_id/organization_unit_id/user_id` 全部 NOT NULL；分别以 `(tree_id,scope_type,company_id,project_id)`、`(tree_id,organization_unit_id)`、`(project_id,user_id)` 引用项目树、组织单元和 project member。
- `positions` 使用与树相同的 company/project 行形状 CHECK，company_id 始终 NOT NULL；project 行以 `(company_id,project_id)` 引用 `projects(company_id,id)`，并明确建立 `UNIQUE(id,scope_type,company_id)` 与 `UNIQUE(id,scope_type,company_id,project_id)`。
- 企业岗位任职表不携带 `project_id`，所有 scope 键 NOT NULL，以 `(position_id,scope_type,company_id)` 和 `(company_id,user_id)` 组合 FK；项目岗位任职表的 project_id NOT NULL，以 `(position_id,scope_type,company_id,project_id)` 和 `(project_id,user_id)` 组合 FK。关系表拆分及非空约束用于避免 PostgreSQL `MATCH SIMPLE` 因任一列为 NULL 而跳过组合 FK。
- `organization_units` 的同父名称唯一使用两个索引：根节点 `UNIQUE(tree_id,name_key) WHERE parent_id IS NULL`，非根节点 `UNIQUE(tree_id,parent_id,name_key) WHERE parent_id IS NOT NULL`。模板节点同理，根节点使用 `UNIQUE(template_id,template_version,name_key) WHERE parent_id IS NULL`，非根节点增加 parent_id；普通含 NULL 的 UNIQUE 不能代替这两个约束。
- 所有新增表中的 `name_key/code_key` 均以 CHECK 校验其等于 `lower(normalize(btrim(原值), NFKC))`；迁移使用同一 PostgreSQL 表达式写入，shared 规范化方法必须用包含全角、组合字符和大小写的固定语料验证与数据库结果一致。`companies` 不新增 `name_key`。
- 既有 `companies.code` 不新增字段，改用上述规范表达式的全局唯一函数索引；既有 `projects.code` 使用 `company_id + 规范表达式` 的企业内唯一函数索引。新索引建立前必须先通过第 2.2 节预检，建立后才能移除被其覆盖的旧大小写敏感唯一约束。
- leader 唯一使用 `WHERE duty = 'leader'` 的部分唯一索引；deputy 和 member 不受人数限制。
- `organization_units.source_template_unit_id` 与 `positions.source_template_position_id` 可空且 RESTRICT，只有项目模板复制生成的数据填写；它们只表示来源，不建立同步关系。
- 组织、岗位、模板均无 DELETE Controller。关系替换可以删除不再存在的关系行，历史由审计保留。

## 6. 事务、并发、查询与审计

### 6.1 写事务

- 所有本期管理写操作继续使用 PostgreSQL `pg_advisory_xact_lock(7421, 1)`。取得锁后必须重新执行登录状态、作用域成员资格、管理员身份、页面+操作权限、资源归属和 expectedVersion 校验。
- 写事务沿用现有 READ COMMITTED；组织默认 sort、组织循环／深度、leader 唯一、模板版本与默认模板唯一都在锁内基于最新已提交状态计算。
- 企业创建、项目创建／模板复制、按成员或按组织单元／岗位的批量关系替换、成员移除清理、模板定义／状态快照和对应成功审计必须在同一事务提交。任何步骤失败全部回滚，且没有成功审计。
- 数据库唯一索引是并发兜底，服务层应把已知约束映射为约定业务错误；未知数据库或程序异常交全局过滤器，不做大范围 catch 后伪装成 503。

### 6.2 只读查询

- 组织树、模板详情和候选聚合等多查询读取继续使用 REPEATABLE READ + READ ONLY，确保树、路径、成员标签和分页总数来自同一快照。
- Repository 查询必须在 SQL 条件中同时约束 companyId/projectId/treeId；禁止先按裸 ID 读取其他租户资源再在 Controller 过滤。
- 候选搜索 trim 后最多 100 字，分页沿用默认 20、最大 100；数组筛选每类最多 100 个去重 UUID。

### 6.3 审计动作

新增固定 action：

```text
organization.unit.create
organization.unit.update
organization.unit.move
organization.unit.status
organization.members.replace
position.create
position.update
position.status
position.members.replace
organization_template.create
organization_template.replace
organization_template.status
project.organization.initialize
```

- action 的企业／项目范围由 `AuditRecord.scope` 区分，不复制两套 action 名。
- 摘要只保存对象 ID、changedFields、from/to、数量、目标 userId、模板 ID／版本等白名单；不得记录密码、token、完整请求体或不必要的成员信息。
- `organization.members.replace` 与 `position.members.replace` 同时复用于按成员和按资源替换；摘要必须记录替换方向、目标 userId／organizationUnitId／positionId、变更前后数量及新增／移除／职责变化数量，不能只记录入口名称。
- 设置新默认模板时，目标模板按入口写 `organization_template.create`、`organization_template.replace` 或 `organization_template.status`；被自动取消默认的旧模板另写一条 `organization_template.status`，摘要记录旧／新 version 与 `isDefault: true → false`。相关审计与完整子项版本快照在同一事务提交。
- 企业／项目成员移除的既有审计摘要增加 `removedOrganizationRelationCount`、`removedPositionAssignmentCount`，但仍保持原 action。

## 8. 前端组件与状态契约

- `Selector/src/Selector.tsx` 继续只做出口归类；`BasicTableSelector`、`GlobalAccountSelect`、`OrganizationMemberSelector` 分别作为独立功能目录，不增加一个庞大 mode 组件。
- `GlobalAccountSelect` 是平台账号远程搜索单选，稳定值为 userId，由业务注入 search/resolve request；编辑回显使用候选快照，不从名称反查。
- `OrganizationMemberSelector` 是 Select 风格表单字段 + 弹窗组织浏览器。左侧为当前可见作用域／组织／岗位／角色筛选，右侧为分页人员和已选区；组织节点只做筛选值，已选值统一为 userId，不持久化候选 identity 的 scope。
- 组织树按层懒加载，节点缓存键必须包含完整 AccessScope 与 parentId；`hasChildren=false` 时不得继续请求子节点。由于节点缓存包含 fullPath、depth、effective，重命名、移动或状态变更必须失效受影响节点及所有后代，同时失效会改变 `hasChildren` 的原／新父级列表；如果前端没有可靠的后代依赖索引，必须直接清空当前 AccessScope 的整棵树缓存，不能只失效父级或祖先。
- 企业页面和项目页面各自从现有 workspace 路由进入，页面内部不再提供第二套企业／项目切换器。请求、树、筛选、分页、已选缓存键必须包含完整 AccessScope；切换工作空间时取消旧请求并清空旧状态。
- 同名人员显示姓名、完整账号和来源作用域；同名组织显示企业／项目名称及 fullPath；组织标签与岗位标签分栏，不暗示关联。
- 401 清登录状态，403 刷新一次 access context，404 显示统一不可见，409 保留表单并提示刷新，422 展示可修正业务原因。前端禁用只是体验，服务端始终二次校验 userId 与作用域。

## 9. 成员移除与状态清理

- 移除项目成员：锁内删除该项目的组织关系（包含 leader/deputy）、岗位任职和项目 user_roles，再删除 project member，写一条既有成员移除审计及清理数量。
- 移除企业成员：锁内先按现有规则处理该企业直接项目中的项目成员及其组织／岗位／角色关系，再清本企业组织关系、岗位任职和 company user_roles，最后删除 company member。
- 停用成员不删除组织或岗位关系，但不再作为新增关系的有效候选；恢复后按当前保存关系重新可见。停用期间允许全量替换请求原样保留或移除既有关系，并允许组织职责降级；禁止新增关系或职责升级。停用组织单元／岗位遵循同一“可保留、可解除、不可新增”规则。
- 任何企业清理不得触碰该 userId 在其他企业中的独立成员、组织、岗位或角色关系。

## 11. 明确排除与禁止字段

本期不得新增以下表、字段、DTO、端点、权限或 UI：

- 项目小组或第四种组织／访问作用域。
- 企业间父子关系，以及企业级父级、企业类型、企业名称规范键、企业排序同义字段、企业树查询／移动端点、企业层级权限或审计动作。
- 主归属、默认组织、primaryOrganization、isPrimary 等同义字段。
- 任何成员手工排序字段或双框排序交互。
- 岗位到组织单元、组织树、模板组织节点的持久关联。
- 企业目标发布、WorkflowTargetSelector、运行时接收人解析、任务参与者、任务级资源／附件授权、流程转交机制或可执行工作流引擎。

“项目 → 直接所属企业”仅是后续工作流专项的首个推荐方向，本期不建表、不加接口、不加权限、不计入验收完成。

## 12. 前后端并行边界与确认门

契约确认后的实施顺序固定为：

1. 契约／架构负责人先独占 `packages/shared`、数据库 schema 与 migration，完成共享导出、权限／错误目录、空库和存量库迁移验证。
2. 共享契约稳定后，后端负责 `apps/server` 的 Controller、Service、Repository、事务、审计与集成测试；前端负责 `apps/web` 的路由、页面、选择器和组件测试，两边并行但只消费 shared 类型。
3. 集成阶段验证全部 45 个实际受影响端点（41 个契约表端点及 4 个既有行为变更端点）、21 个权限 key、7 个组织领域新增错误码、成员移除清理和 AC-01～AC-36；企业邀请细节确认后另行进入成员接入契约和验证范围，现有邀请实现不得提前计入。
4. QA 默认使用真实 PostgreSQL 集成测试和 Playwright 覆盖关键 Web 流程；环境无法验证必须明确标记，不能算通过。
